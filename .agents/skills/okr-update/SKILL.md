# OKR 进展记录

你在维护一份 OKR 进展记录。它要回答四个问题：每个 KR 现在到了哪里、凭什么这么说、下一步做什么、卡在哪里。

读者有三类：用户本人；之后接手的 agent 会话；用户的 leader（通过周报）。写的时候优先照顾第二类：它没有本次对话的任何上下文，只读 `progress.md` 就必须能直接开工。

## 0. 配置

- `OKR_DIR=~/notes/okr/2026Q4`（每个 OKR 周期只改这一行）。文件工具需要绝对路径时，用 `echo $HOME` 展开 `~`。
- 日期和周号一律用命令获取：`date '+%F %H:%M'`、`date +%G-W%V`。记录里只写绝对日期，不写"昨天""下周"。

## 1. 文件与写入规则

| 文件 | 内容 | 写入规则 |
|---|---|---|
| `okr.md` | O、KR 定义、口径、基线、目标、数据源 | 只读（`init` 模式除外）。认为 KR 需要调整时，写进 `progress.md` 的「待确认」 |
| `progress.md` | 总览、待确认事项、每个 KR 的状态快照 | 就地更新，只改本次涉及的小节 |
| `log/<YYYY-Www>.md` | 按时间追加的事件 | 只追加，不改、不删旧条目；纠错就追加一条「更正」 |
| `reports/<YYYY-Www>.md` | 周报 | 由 `report` 模式生成 |

- 写入前重新读取目标文件：其他仓库里的 agent 会话可能刚改过它。用局部编辑，不要整文件覆盖。
- `OKR_DIR` 或其中的文件不存在时，提示用户先运行 `init`，不要自己编造 OKR。

## 2. 选择模式

看调用参数（在 Codex 中，即用户消息里 `$okr-update` 后面的内容）：以 `init`、`collect`、`report` 开头的，按对应模式处理；其余文本视为笔记；没有参数，或者由常驻规则触发时，执行会话收尾。

| 参数 | 模式 | 进展来源 | 写入前要不要用户确认 |
|---|---|---|---|
| 空 | 会话收尾 | 本次会话中你自己完成的工作 | 不要 |
| 一段文本 | 归档笔记 | 用户提供的纪要、聊天、笔记 | 不要；KR 归属不明确时先问 |
| `collect [起始日期]` | 主动采集 | `okr.md` 中的「数据源」 | 要 |
| `report [周号]` | 生成周报 | 日志与 `progress.md` | 不要 |
| `init` | 初始化 | 用户提供的 OKR 原文 | 缺失字段先问 |

确认门槛随来源变化，因为可信度不同：你亲手做的事，你知道结果；用户说的事，由用户负责；从 commit 和日志推断出的"进展"最容易张冠李戴。

## 3. 记录原则（所有模式适用）

1. **结果优先于产出。** "代码合入了""实验跑完了"是产出；KR 关心的是指标或里程碑有没有动。指标型 KR 的进度只能由符合 KR 口径的实测值推动。产出写进日志和「最近进展」，但不改变进度。
2. **每条进展都要有证据。** 证据可以是 commit hash、PR 链接、实验 ID 或日志路径、看板链接、文档链接，或"用户口述（日期）"。拿不出证据的，写成"未验证"。
3. **注明测量环境。** 离线、压测、灰度、全量的结果不能混为一谈。KR 口径是线上指标时，离线或压测结果只能写成"压测 xx，线上待验证"，不能据此改进度，也不能据此把状态改为「已完成」。
4. **不夸大，不替用户下结论。** 笔记里模糊的说法（"差不多了""应该能上"）原样引用并标"待确认"，不要改写成确定的事实。
5. **标注来源。** 每条日志写明来源：`agent(<工具>@<仓库>)`、`user` 或 `collect`。
6. **状态只按第 5 节的规则变化。** 降级（例如 正常 → 有风险）可以直接改，并写明理由；升到「已完成」必须有符合 KR 口径的实测证据；「已调整」只能由用户决定。
7. **保持简短。** 每个 KR 小节不超过 15 行，「最近进展」只保留最近 3 条，每条日志不超过 6 行。详细过程留在 commit、PR、实验记录里，记录中只放链接。
8. **安全。** 不写入密钥、token、账号密码，也不写入用户数据样本。
9. **语言。** 用中文书写，技术术语、服务名、指标名保留英文原文。

## 4. 各模式的流程

### 4.1 会话收尾（默认模式）

1. 回顾本次会话做了什么，逐项区分：已验证（测试通过、实验跑完、指标实测）还是完成了但未验证。
2. 把每一项归到一个 KR。归不进任何 KR 的不记。一项工作同时推进多个 KR 时，记在主要的 KR 下，其他 KR 写一句引用。
3. 在 `log/<本周>.md` 末尾追加日志条目（模板 6.3）。文件不存在就先建好，写上标题。
4. 更新 `progress.md` 中涉及的部分：KR 小节（当前值、里程碑、状态、风险/阻塞、最近进展）、「总览」表中对应的行、文件头的「最后更新」和「时间进度」。
5. 按第 5 节的规则重新规划该 KR 的「下一步」。
6. 向用户汇报，不超过 5 行：改了哪些 KR、状态有没有变化、新的下一步第一条是什么、有哪些待确认的问题。

### 4.2 归档笔记

1. 把文本拆成独立事件：进展、决策、风险、计划变更。
2. 逐条归到 KR。归属不明确的，汇总成一个问题一次问完，不要猜。
3. 按 4.1 的第 3–6 步写入。来源记为 `user`；证据记为"用户口述（日期）"或用户给出的链接。
4. 笔记里只有用户能确认的数字（例如线上指标），原样记录并注明出处，不要自行换算或补全。

### 4.3 主动采集

1. 确定起点，优先级从高到低：参数给出的起始日期、`progress.md` 中的「上次采集」、7 天前。
2. 读取 `okr.md` 的「数据源」，逐项采集。只读，不修改任何仓库。
   - git：`git -C <repo> log --since=<起点> --author=<作者> --no-merges --date=short --format='%h %ad %s'`
   - PR / 代码评审：用数据源里给出的命令或工具；不可用就跳过，并在结果里说明。
   - 实验与压测记录：读取数据源里列出的目录或文件。
3. 去重：commit hash、PR 编号、实验 ID 已经出现在日志里的，跳过。
4. 把结果整理成候选更新表，交给用户确认：

   | # | 证据 | 推断归属 | 推断的进展 | 把握（高/中/低） |
   |---|---|---|---|---|

   把握为"低"的行，在表后逐条说明原因。
5. 用户逐条接受、修改或拒绝之后，再按 4.1 的第 3–6 步写入，来源记为 `collect`。
6. 如果当前没有用户在场确认（例如定时任务），只把候选更新写进日志（类型为「待确认」）并加入 `progress.md` 的「待确认」，不改任何状态、数值和下一步。
7. 最后把 `progress.md` 的「上次采集」更新为本次采集的时间。

### 4.4 生成周报

1. 周号取参数，默认本周。读取 `log/<周号>.md`、上一周的日志（用于对比）和 `progress.md`。
2. 只使用已确认的内容。未验证的进展要么不写，要么注明"（待验证）"；「待确认」中的事项不写入周报正文。
3. 按模板 6.4 写入 `reports/<周号>.md`，并把全文展示给用户。
4. 写法：每条先说结果，再给数据和证据链接；数字带单位和测量环境；过程细节不进周报。全文控制在一页以内。

### 4.5 初始化

1. 把用户提供的 OKR 原文（可能来自 OKR 系统，也可能是口述）整理成 `okr.md`（模板 6.1）。
2. 检查每个 KR 是否齐备：类型（指标型或里程碑型）、口径、基线、目标、截止日期；里程碑型 KR 还要有里程碑列表。缺失的字段汇总成一组问题一次问完；用户也不知道的，填"待补充"。
3. 询问数据源：相关仓库路径、git 作者名、实验记录位置、PR 的查询方式、指标看板。
4. 创建 `progress.md`（模板 6.2，所有 KR 状态为「未开始」，各给出初始的下一步）、`log/` 和 `reports/`，并在本周日志里记一条「初始化」。

## 5. 状态、进度与下一步

**状态**（只用这六个）：

| 状态 | 条件 |
|---|---|
| 未开始 | 还没有任何进展证据 |
| 正常 | 有进展，且没有明显落后于时间进度 |
| 有风险 | 进度明显落后于时间进度（例如时间过半而进度不到三分之一），或者存在可能影响结果、尚未解决的依赖或技术不确定性 |
| 受阻 | 当前无法推进，需要外部条件（他人配合、资源、审批）解除 |
| 已完成 | 按 KR 口径实测达标，并有证据 |
| 已调整 | 用户决定修改、暂停或放弃该 KR |

**进度**：

- 指标型：`进度 = (当前值 − 基线) / (目标 − 基线)`，越低越好的指标同样适用。同时写出基线、当前值、目标三个原始数值及测量环境；百分比只是辅助。
- 里程碑型：写"已完成 k / n 个里程碑"，不折算成百分比。
- 时间进度：`(今天 − 周期开始) / (周期结束 − 周期开始)`。

**下一步**：

1. 从差距出发。先问"离目标还差什么、哪一步最能缩小差距"，而不是罗列待办事项。
2. 每个 KR 最多 3 条，按优先级排列。第一条必须具体到下一个会话可以直接开工：写清要改的模块、要跑的实验或命令。
3. 每条写明完成标准，并标注执行者：`[agent]` 表示 agent 可以独立完成；`[人工]` 表示需要用户本人、他人配合、资源或审批。
4. 删掉或调整了上次的下一步时，在日志里追加一条「计划变更」，写明原因。

## 6. 模板

### 6.1 okr.md

```markdown
# OKR · <周期，如 2026Q4>

- 周期：<开始日期> ~ <结束日期>
- 负责人：<姓名>

## O1：<目标>

### KR1：<关键结果原文>
- 类型：指标型
- 口径：<指标名、统计范围、环境、统计方式>
- 基线：<数值>（<测量日期>）
- 目标：<数值>
- 截止：<日期>

### KR2：<关键结果原文>
- 类型：里程碑型
- 里程碑：
  - M1 <描述>（计划 <日期>）
  - M2 <描述>（计划 <日期>）
- 截止：<日期>

## 数据源（collect 模式使用）
- 仓库：<路径>（git 作者：<作者名或邮箱>）
- PR / 代码评审：<查询方式或命令；没有就写"无">
- 实验与压测记录：<目录或文件>
- 指标看板：<链接>（agent 无法访问时，由用户提供数值）
```

### 6.2 progress.md

```markdown
# OKR 进展 · <周期>

> 最后更新：<YYYY-MM-DD HH:MM>（<来源>）｜上次采集：<YYYY-MM-DD HH:MM，或"无">
> 周期：<开始> ~ <结束>｜时间进度：<x>%

## 总览

| KR | 状态 | 进度 | 一句话现状 |
|---|---|---|---|
| KR1 | <状态> | <当前 / 目标，x%> | <不超过 20 字> |
| KR2 | <状态> | <k / n 个里程碑> | <不超过 20 字> |

## 待确认

- [ ] <YYYY-MM-DD>（<来源>）<需要用户确认或决定的事>

## KR1：<关键结果原文>

- 状态：<状态>（自 <日期>）
- 当前：<数值>（<环境>，<日期>，证据：<链接>）｜基线 <数值>｜目标 <数值>｜进度 <x>%
- 风险/阻塞：<无，或具体描述>
- 下一步：
  1. [agent] <具体动作> —— 完成标准：<……>
  2. [人工] <具体动作> —— 完成标准：<……>
- 最近进展：
  - <YYYY-MM-DD> <一句话>（详见 log/<YYYY-Www>.md）

## KR2：<关键结果原文>

- 状态：<状态>（自 <日期>）
- 里程碑：
  - [x] M1 <描述>（<完成日期>，证据：<链接>）
  - [ ] M2 <描述>
- 风险/阻塞：<……>
- 下一步：<同 KR1 的格式>
- 最近进展：<同 KR1 的格式>
```

### 6.3 日志条目

周文件的第一行是标题 `# <YYYY-Www>`，之后逐条追加：

```markdown
### <YYYY-MM-DD HH:MM> · <KR 编号> · <类型> · 来源：<agent(工具@仓库) | user | collect>
- 内容：<发生了什么，结果在前>
- 证据：<commit / PR / 实验 ID / 链接 / 用户口述（日期）>
- 理由：<仅「决策」和「计划变更」需要>
- 状态变化：<旧状态 → 新状态；没有变化就省略这一行>
```

类型只用：进展、决策、风险、计划变更、更正、待确认、初始化。

### 6.4 周报

```markdown
# 周报 · <YYYY-Www>（<周一日期> ~ <周日日期>）

**本周结论**：<一两句话：整体状态，以及最重要的变化>

| KR | 状态 | 当前 / 目标 | 本周变化 |
|---|---|---|---|
| KR1 | <状态> | <当前 / 目标> | <变化，注明环境> |

## 主要进展
- **KR1**：<结果>。<数据（环境）>。[证据](<链接>)

## 风险与需要的支持
- <风险> → <可能的影响> → <应对；需要谁在什么时候做什么>

## 下周计划
- **KR1**：<计划，取自 progress.md 的下一步>
```
