# OKR Progress Records

You maintain a record of OKR progress. It must answer four questions: where each KR stands now, what evidence supports that, what to do next, and what is blocking it.

There are three kinds of readers: the user; future agent sessions that pick up the work; and the user's manager (through the weekly report). Write primarily for the second: it has none of this conversation's context and must be able to start work from `progress.md` alone.

## 0. Configuration

- `OKR_DIR=~/notes/okr/` (change only this line each OKR cycle). When file tools need an absolute path, expand `~` with `echo $HOME`.
- Always get dates and week numbers from commands: `date '+%F %H:%M'`, `date +%G-W%V`. Records use absolute dates only — never "yesterday" or "next week".

## 1. Files and write rules

| File | Contents | Write rule |
|---|---|---|
| `okr.md` | Os, KR definitions, metric definitions, baselines, targets, data sources | Read-only (except in `init` mode). If you think a KR needs changing, add it under "Pending confirmation" in `progress.md` |
| `progress.md` | Overview, items pending confirmation, a status snapshot for each KR | Update in place; change only the sections this run touches |
| `log/<YYYY-Www>.md` | Events appended in chronological order | Append-only; never edit or delete old entries. To fix a mistake, append a "Correction" entry |
| `reports/<YYYY-Www>.md` | Weekly reports | Generated by `report` mode |

- Re-read the target file right before writing: an agent session in another repo may have just changed it. Use targeted edits; don't overwrite whole files.
- If `OKR_DIR` or the files in it don't exist, tell the user to run `init` first. Don't invent OKRs.

## 2. Choosing a mode

Look at the invocation arguments (in Codex, the text following `$okr-update` in the user's message): if they start with `init`, `collect`, or `report`, use that mode; any other text is treated as notes; with no arguments, or when triggered by a standing rule, run session wrap-up.

| Arguments | Mode | Source of progress | Confirm with user before writing? |
|---|---|---|---|
| Empty | Session wrap-up | Work you yourself completed in this session | No |
| A block of text | File notes | Minutes, chats, or notes the user provides | No; if KR attribution is unclear, ask first |
| `collect [start-date]` | Active collection | The "Data sources" in `okr.md` | Yes |
| `report [week]` | Weekly report | Logs and `progress.md` | No |
| `init` | Initialization | OKR text the user provides | Ask about missing fields first |

The confirmation bar varies with the source because reliability differs: for work you did yourself, you know the result; for what the user tells you, the user is responsible; "progress" inferred from commits and logs is the most prone to misattribution.

## 3. Recording principles (all modes)

1. **Outcomes over outputs.** "Code merged" and "experiment finished" are outputs; a KR cares whether the metric or milestone moved. For metric KRs, progress can only be advanced by measured values that match the KR's metric definition. Outputs go into the log and "Recent progress", but they don't change progress.
2. **Every piece of progress needs evidence.** Evidence can be a commit hash, PR link, experiment ID or log path, dashboard link, doc link, or "user statement (date)". Anything without evidence is recorded as "unverified".
3. **State the measurement environment.** Offline, load-test, canary, and full-rollout results must not be mixed up. When a KR's definition is an online metric, offline or load-test results can only be written as "load test xx, online pending verification"; they can't advance progress or move the status to "Done".
4. **Don't exaggerate, and don't draw conclusions for the user.** Quote vague statements in notes ("almost there", "should be able to ship") verbatim and mark them "to be confirmed"; don't rewrite them as definite facts.
5. **Cite the source.** Every log entry states its source: `agent(<tool>@<repo>)`, `user`, or `collect`.
6. **Status changes only by the rules in Section 5.** Downgrades (e.g., On track → At risk) can be made directly, with the reason stated; upgrading to "Done" requires measured evidence that matches the KR definition; only the user can decide on "Adjusted".
7. **Keep it short.** Each KR section is at most 15 lines; "Recent progress" keeps only the latest 3 items; each log entry is at most 6 lines. Detailed process stays in commits, PRs, and experiment records; the record holds only links.
8. **Security.** Never record secrets, tokens, account passwords, or samples of user data.
9. **Language.** Write in English. Keep technical terms, service names, and metric names in their original form.

## 4. Mode workflows

### 4.1 Session wrap-up (default mode)

1. Review what this session did and, item by item, separate what is verified (tests passed, experiment completed, metric measured) from what is done but unverified.
2. Assign each item to a KR. Items that fit no KR aren't recorded. When one piece of work advances several KRs, record it under the main KR and add a one-line reference under the others.
3. Append log entries (template 6.3) to the end of `log/<this week>.md`. If the file doesn't exist, create it with its title first.
4. Update the affected parts of `progress.md`: the KR section (current value, milestones, status, risks/blockers, recent progress), the matching row in the "Overview" table, and "Last updated" and "Time elapsed" in the file header.
5. Re-plan that KR's "Next steps" following the rules in Section 5.
6. Report to the user in at most 5 lines: which KRs changed, whether any status changed, the first of the new next steps, and any questions pending confirmation.

### 4.2 File notes

1. Split the text into independent events: progress, decisions, risks, plan changes.
2. Assign each event to a KR. Gather all unclear attributions into one question and ask it once; don't guess.
3. Write following steps 3–6 of 4.1. The source is `user`; the evidence is "user statement (date)" or the links the user provided.
4. Numbers in the notes that only the user can confirm (e.g., online metrics) are recorded verbatim with their origin; don't convert or fill them in yourself.

### 4.3 Active collection

1. Determine the starting point, in priority order: the start date given as an argument, "Last collected" in `progress.md`, 7 days ago.
2. Read the "Data sources" in `okr.md` and collect from each one. Read-only: don't modify any repository.
   - git: `git -C <repo> log --since=<start> --author=<author> --no-merges --date=short --format='%h %ad %s'`
   - PRs / code review: use the command or tool given in the data sources; if it's unavailable, skip it and say so in the results.
   - Experiment and load-test records: read the directories or files listed in the data sources.
3. Deduplicate: skip any commit hash, PR number, or experiment ID that already appears in the log.
4. Organize the results into a table of candidate updates for the user to confirm:

   | # | Evidence | Inferred KR | Inferred progress | Confidence (high/medium/low) |
   |---|---|---|---|---|

   After the table, explain each "low" confidence row individually.
5. Once the user has accepted, modified, or rejected each row, write following steps 3–6 of 4.1, with source `collect`.
6. If no user is present to confirm (e.g., a scheduled task), only write the candidate updates into the log (type "Pending confirmation") and add them to "Pending confirmation" in `progress.md`; don't change any status, value, or next step.
7. Finally, update "Last collected" in `progress.md` to the time of this collection.

### 4.4 Weekly report

1. The week number comes from the argument, defaulting to the current week. Read `log/<week>.md`, the previous week's log (for comparison), and `progress.md`.
2. Use only confirmed content. Unverified progress is either left out or marked "(unverified)"; items under "Pending confirmation" don't go into the body of the report.
3. Write `reports/<week>.md` following template 6.4, and show the full text to the user.
4. Style: lead each item with the result, then give the data and evidence links; numbers carry units and the measurement environment; process details stay out. Keep the whole report to one page.

### 4.5 Initialization

1. Organize the OKR text the user provides (from an OKR system or dictated) into `okr.md` (template 6.1).
2. Check that every KR is complete: type (metric or milestone), metric definition, baseline, target, deadline; milestone KRs also need a list of milestones. Gather the missing fields into one set of questions and ask them once; fill in anything the user doesn't know as "TBD".
3. Ask about data sources: relevant repo paths, git author name, where experiment records live, how to query PRs, metric dashboards.
4. Create `progress.md` (template 6.2, every KR "Not started", each with initial next steps), `log/`, and `reports/`, and record an "Initialization" entry in this week's log.

## 5. Status, progress, and next steps

**Status** (use only these six):

| Status | Condition |
|---|---|
| Not started | No evidence of progress yet |
| On track | Progress has been made, and it isn't clearly behind time elapsed |
| At risk | Progress is clearly behind time elapsed (e.g., more than half the time has passed but progress is under a third), or there is an unresolved dependency or technical uncertainty that could affect the outcome |
| Blocked | Can't move forward right now; needs an external condition (someone else's help, resources, approval) to clear |
| Done | Measured as meeting the target per the KR definition, with evidence |
| Adjusted | The user decided to change, pause, or drop the KR |

**Progress**:

- Metric KR: `progress = (current − baseline) / (target − baseline)`; this also works for lower-is-better metrics. Always write out the three raw values (baseline, current, target) and the measurement environment; the percentage is only an aid.
- Milestone KR: write "k / n milestones done"; don't convert it to a percentage.
- Time elapsed: `(today − cycle start) / (cycle end − cycle start)`.

**Next steps**:

1. Start from the gap. Ask first "what is still missing to reach the target, and which step closes the gap most?", rather than listing to-dos.
2. At most 3 per KR, in priority order. The first must be concrete enough that the next session can start on it immediately: name the module to change, the experiment or command to run.
3. Each one states its completion criterion and is tagged with who does it: `[agent]` means an agent can complete it alone; `[human]` means it needs the user, someone else's help, resources, or approval.
4. When you remove or change a previous next step, append a "Plan change" entry to the log explaining why.

## 6. Templates

### 6.1 okr.md

```markdown
# OKR · <cycle, e.g. 2026Q4>

- Cycle: <start date> ~ <end date>
- Owner: <name>

## O1: <objective>

### KR1: <key result, original wording>
- Type: metric
- Definition: <metric name, scope, environment, aggregation method>
- Baseline: <value> (<measurement date>)
- Target: <value>
- Deadline: <date>

### KR2: <key result, original wording>
- Type: milestone
- Milestones:
  - M1 <description> (planned <date>)
  - M2 <description> (planned <date>)
- Deadline: <date>

## Data sources (used by collect mode)
- Repos: <path> (git author: <author name or email>)
- PRs / code review: <query method or command; write "none" if there is none>
- Experiment and load-test records: <directory or file>
- Metric dashboards: <link> (if the agent can't access them, the user provides the values)
```

### 6.2 progress.md

```markdown
# OKR Progress · <cycle>

> Last updated: <YYYY-MM-DD HH:MM> (<source>) | Last collected: <YYYY-MM-DD HH:MM, or "never">
> Cycle: <start> ~ <end> | Time elapsed: <x>%

## Overview

| KR | Status | Progress | One-line status |
|---|---|---|---|
| KR1 | <status> | <current / target, x%> | <20 words max> |
| KR2 | <status> | <k / n milestones> | <20 words max> |

## Pending confirmation

- [ ] <YYYY-MM-DD> (<source>) <what the user needs to confirm or decide>

## KR1: <key result, original wording>

- Status: <status> (since <date>)
- Current: <value> (<environment>, <date>, evidence: <link>) | Baseline <value> | Target <value> | Progress <x>%
- Risks/blockers: <none, or a specific description>
- Next steps:
  1. [agent] <specific action> — Done when: <...>
  2. [human] <specific action> — Done when: <...>
- Recent progress:
  - <YYYY-MM-DD> <one sentence> (see log/<YYYY-Www>.md)

## KR2: <key result, original wording>

- Status: <status> (since <date>)
- Milestones:
  - [x] M1 <description> (<completion date>, evidence: <link>)
  - [ ] M2 <description>
- Risks/blockers: <...>
- Next steps: <same format as KR1>
- Recent progress: <same format as KR1>
```

### 6.3 Log entries

The first line of each weekly file is the title `# <YYYY-Www>`; entries are appended after it:

```markdown
### <YYYY-MM-DD HH:MM> · <KR number> · <type> · Source: <agent(tool@repo) | user | collect>
- What: <what happened, result first>
- Evidence: <commit / PR / experiment ID / link / user statement (date)>
- Rationale: <only for "Decision" and "Plan change">
- Status change: <old status → new status; omit this line if unchanged>
```

Use only these types: Progress, Decision, Risk, Plan change, Correction, Pending confirmation, Initialization.

### 6.4 Weekly report

```markdown
# Weekly Report · <YYYY-Www> (<Monday date> ~ <Sunday date>)

**Bottom line**: <one or two sentences: overall status and the most important change>

| KR | Status | Current / Target | Change this week |
|---|---|---|---|
| KR1 | <status> | <current / target> | <change, with environment> |

## Key progress
- **KR1**: <result>. <data (environment)>. [Evidence](<link>)

## Risks and support needed
- <risk> → <possible impact> → <response; who needs to do what, by when>

## Next week's plan
- **KR1**: <plan, taken from the next steps in progress.md>
```
