# D2C Context Contract Spec

Use this reference when generating or repairing a `d2c_context` folder.

## Contract Instance

`d2c.contract.json` should be business-generated. It is not a JSON Schema. It is the per-task contract that tells the D2C agent what must be true for this page/component.

Minimal shape:

```json
{
  "schemaVersion": "d2c-context/v1",
  "target": {
    "platform": "lynx-ttml",
    "styleLanguage": "less",
    "unit": "rpx"
  },
  "dependencyPolicy": {
    "componentMappingFirst": true,
    "installMissingMappedPackages": true,
    "registryFallback": ["https://registry.example.com"],
    "fallbackRequiresEvidence": true
  },
  "componentMappings": [],
  "tokenMappings": [],
  "dataProtocolMappings": [],
  "agentRuleFiles": [
    "rules.md",
    "platform/lynx.md"
  ],
  "validation": {
    "typecheck": "required",
    "visualEval": "required-after-render"
  }
}
```

## Required Semantics

The contract folder must preserve both machine-readable constraints and agent-facing execution prompts. The machine-readable source is `d2c.contract.json`; the generated prompt source is `AGENT_GUIDE.md`; business-authored prompt sources live in files referenced by `agentRuleFiles`.

### target

Declare platform and unit rules. Examples:

- `platform`: `lynx-ttml`, `lynx-react`, `browser-react`
- `styleLanguage`: `less`, `css`, `scss`
- `unit`: `rpx` or `px`. This is the source of truth for all generation and refine evidence. `px` consumers must read raw values from `origin.json` even if `origin.rpx.json` exists; `rpx` consumers prefer `origin.rpx.json`.
- Before visual segmentation, map this value to `config.unit` and pass it with the rest of the segmentation config.

### dependencyPolicy

Declare dependency and fallback behavior. Use the registry URL required by the target business or deployment environment.

```json
{
  "componentMappingFirst": true,
  "installMissingMappedPackages": true,
  "registryFallback": ["https://registry.example.com"],
  "fallbackRequiresEvidence": true
}
```

This means an agent must not use primitive fallback just because a mapped package is missing. It must first install `packageName@targetVersion`; if registry/private package resolution fails, it must configure or otherwise use a registry from `registryFallback` and retry.

### componentMappings

Each mapped component should describe the business-owned mapping from a Figma node to a target component package. Use concrete values generated by the business integration. Do not copy examples from another product or component library.

```json
{
  "nodeId": "<figma-node-id>",
  "nodeName": "<figma-node-name>",
  "packageName": "<component-package-name>",
  "componentName": "<component-export-or-tag-name>",
  "targetVersion": "<package-version-or-range>",
  "variantProperties": {
    "<variant-key>": "<variant-value>"
  },
  "props": {
    "<prop-name>": "<prop-value-or-binding>"
  },
  "propsPatch": {
    "<prop-name>": "<override-value-or-binding>"
  },
  "tokenMappingIds": ["<token-mapping-id>"],
  "decisionStatus": "ready"
}
```

Required fields: `nodeId`, `packageName`, `componentName`, `targetVersion`.

Agent-facing semantics that must be reflected in `AGENT_GUIDE.md`:

- Treat `componentMappings[]` as the first lookup table when a user selects or references a component.
- Locate mappings by `nodeId` first when available, then by `componentName` when a stable node id is not available.
- After resolving the mapping, read the referenced design protocol node by the same `nodeId` to get structure, styles, text, assets, and child evidence.
- Use `packageName`, `targetVersion`, `variantProperties`, `props`, `propsPatch`, and `tokenMappingIds` from the mapping. Do not invent package names, versions, variants, or props from memory.
- Primitive implementation is a fallback path only after mapped component installation, import/registration, target-platform entry, or runtime validation fails with recorded evidence.

### tokenMappings

Map Figma variables to code tokens. `codeUsage` is intentionally open-ended: different businesses may use Less variables, CSS custom properties, Sass variables, JS theme objects, generated token modules, or no import at all. Include only the import/snippet required by the target project.

```json
{
  "id": "<token-mapping-id>",
  "designToken": "<figma-variable-or-style-name>",
  "rawValue": "<resolved-design-value>",
  "codeToken": "<project-token-reference>",
  "codeUsage": {
    "language": "<css|less|scss|js|ts>",
    "import": "<optional-project-token-import>",
    "snippet": "<optional-usage-snippet>"
  },
  "usages": [
    {
      "nodeId": "<figma-node-id>",
      "styleKeys": ["<style-property>"]
    }
  ]
}
```

If the project uses raw values instead of token imports, keep `codeToken` as the resolved value and omit `codeUsage.import`.

Agent-facing semantics that must be reflected in `AGENT_GUIDE.md`:

- When a design style uses a token or variable present in `tokenMappings[]`, apply the mapped `codeToken`/`codeUsage` before hardcoding the resolved fallback value.
- Check both the selected component's `tokenMappingIds` and token usages discovered on descendant design nodes.
- Respect the target project's style pipeline. A Less import, CSS custom property, Sass variable, generated module, or raw value are all valid when declared by the contract.
- If token usage cannot be supported by the target runtime, record the reason and fallback value instead of silently dropping the mapping.

### dataProtocolMappings

Use this section for visual states that real components reveal only through runtime data, not direct style. This prevents the agent from guessing data fields by reading component source during implementation.

Generic example for a component badge or status mark:

```json
{
  "id": "<data-protocol-mapping-id>",
  "figmaEvidence": {
    "nodeId": "<figma-node-id>",
    "nodeName": "<figma-node-name>",
    "componentName": "<figma-component-or-instance-name>"
  },
  "targetComponent": "<component-package-or-name>",
  "requiredState": [
    {
      "dataPath": "<runtime-data-path>",
      "valueKind": "<non_empty_string|boolean_true|enum|object|array_non_empty>",
      "reason": "<why-this-data-state-is-required>"
    },
    {
      "dataPath": "<optional-additional-runtime-data-path>",
      "value": "<required-literal-value-or-object>",
      "reason": "<why-this-additional-state-is-required>"
    }
  ]
}
```

Use `dataProtocolMappings` for badges, live rings, AI states, disabled/follow states, remote image variants, experiment states, and any component visual that depends on non-style business data.

Agent-facing semantics that must be reflected in `AGENT_GUIDE.md`:

- If Figma evidence shows a visual state controlled by runtime data, use `dataProtocolMappings[]` to set or mock that state during restoration.
- Do not derive required runtime fields by guessing from screenshots. Business-generated protocol fields should provide the data path, value kind, literal value when needed, and reason.
- When a mapped component does not show the expected state, verify that the required runtime data is present before replacing the component with primitives.

### fallbackRecords

When primitive fallback is used, record evidence:

```json
{
  "nodeId": "<figma-node-id>",
  "originalPackageName": "<component-package-name>",
  "attempts": [
    "install <component-package-name>@<version> attempted",
    "<specific integration or runtime failure>"
  ],
  "fallbackReason": "<why-a-primitive-implementation-was-required>",
  "coveredCapabilities": ["<capability-covered-by-fallback>"],
  "missingCapabilities": ["<component-capability-not-covered-by-fallback>"]
}
```

### agentRuleFiles

Use `agentRuleFiles` for business-owned textual rules that are important but awkward or brittle to encode as JSON. These files are similar in spirit to skill instructions, but they are scoped to one business integration or one generated `d2c_context` package.

```json
{
  "agentRuleFiles": [
    "rules.md",
    "platform/lynx.md",
    "team/style-guide.md"
  ]
}
```

Recommended rule file shape:

```markdown
# Coding Style

## Applies To

- lynx-ttml
- browser-react

## Must

- Use the business wrapper around network images.
- Keep generated class names under the configured prefix.

## Must Not

- Import deprecated component entrypoints.
- Inline theme values when a mapped token exists.

## Examples

Short examples are allowed when they are specific to this business integration.
```

Rules for `agentRuleFiles`:

- Paths are relative to the `d2c_context/` directory.
- Files must be markdown.
- They may contain concrete business package names, code style rules, component caveats, data mock conventions, platform constraints, validation commands, and examples.
- They should not duplicate large design evidence or replace `componentMappings`, `tokenMappings`, or `dataProtocolMappings`.
- If a rule contradicts `d2c.contract.json`, the contract wins unless the user explicitly approves changing the contract.
- Agents consuming the context must read `AGENT_GUIDE.md` and all `agentRuleFiles` before implementation.

## AGENT_GUIDE.md

Generate a short guide from the contract. This file intentionally preserves the useful prompt behavior that used to live in ad hoc `d2c_context.md` files, but it must be generated from business-neutral contract fields. Keep it concise and procedural.

Required guide content:

- Source-of-truth rule: read `d2c.contract.json` first, then read referenced design protocol files for the selected page/component.
- Component resolution rule: when a component/page is selected, resolve by `nodeId` or `componentName`, then read the corresponding design node evidence.
- Mapping-first dependency rule: mapped components are attempted before primitive fallback; missing packages are installed as `packageName@targetVersion`.
- Registry retry rule: if configured registry fallback exists, registry/404/private package failures are retried through that configured registry before fallback.
- Fallback evidence rule: fallback must record package, props, install/import/registration/runtime validation results, reason, covered capabilities, and missing capabilities.
- Token rule: mapped design tokens must be applied through the contract's `codeUsage` before hardcoded fallback values.
- Runtime data rule: component visual states described by `dataProtocolMappings[]` must be provided through data/mocks before judging the component visually incorrect.
- Business rules rule: read all markdown files listed in `agentRuleFiles`; apply them as local coding/component/style constraints when they do not contradict the contract.
- Version review rule: fields such as `targetVersion`, `versionAction`, `decisionStatus`, `propsPatch`, or `businessChanges` must not be changed during implementation when the contract marks them as review-required.
- Platform rule: target platform, style language, unit behavior, root container behavior, and validation commands come from the contract and project-local agent instructions.
- Execution checklist: resolve mapping, inspect design protocol node, install/verify dependencies, implement mapped component or recorded fallback, apply tokens/data states, run required validation/evaluation.

Avoid adding long explanations that duplicate the contract.
