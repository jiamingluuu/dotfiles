# DevMind Commands

All examples use JSON mode. These list flags accept either a comma-separated list or the flag
repeated once per value, and repeats accumulate, so both forms can be mixed: `meta --alias`,
`user get --username`, `metric query --member`, `metric query --group-dim`, `query --dimensions`.
`drill get` instead takes a single `--member` and a single `--group-dim` (written `<username>` /
`<id>`); repeating either keeps only the last value.

`--start` / `--end` take either `YYYY-MM-DD` or `"YYYY-MM-DD HH:mm:ss"` (quote the datetime form
so the shell keeps it as one argument). The platform answers a bare date in its `BETWEEN`
condition with an all-empty series, so the CLI anchors a bare `--start` to `00:00:00` and a bare
`--end` to `23:59:59` before sending it — pass dates freely, but a hand-built `--payload-file`
must anchor both ends itself. ISO forms like `2026-07-01T08:00:00` are rejected. An inverted
range is rejected too, since the platform answers that with an empty series as well and a blank
cell is indistinguishable from a metric that genuinely has no data.

## Output Shape

- `doctor` returns `ok`, non-sensitive auth status checks, and optional metric probe metadata. The checks are `bytecloud_jwt` (a JWT was obtained for the DevMind host) and `metric_probe` (`skipped` without `--node-id`); `username` and `auth_code_digits` are reported as metadata rather than as checks, since the Auth-Code is derived locally at a fixed width and a width check could only ever pass. `ok` is false when any check errors, and the command then exits non-zero with `DEVMIND_DOCTOR_FAILED`.
- `node get` returns `{ nodeName, nodePath, depth, spaceType, liaisonOfficers[], raw }` for a report/business node; scalar fields are `null` when the platform omits them. For an employee node the platform answers `nodePath: null`, so use `node search` when a path is what you need.
- `node search` returns `{ nodes, page, pageSize, total }` — the reverse of `node get`: it turns a name into the node id every other DevMind command asks for, each hit being `{ nodeId, displayName, hintContent, nodePath, authorizationType, nodeStatus, userName, raw }` with scalar fields `null` when the platform omits them. Every hit carries a usable `nodePath`, including for employee nodes where `node get` answers `null`, so a search result can be passed straight to `metric list` / `metric query` / `story list` as `--node-id` plus `--node-path`. `--space-type` picks the tree to search and each value answers with its own set rather than a filtered view of one: `employee` (the default) searches people and matches on name or username, `report` searches report nodes and puts the owning department in `hintContent`, `business` searches the business tree and returns slash-joined ancestry as the `displayName` with no `userName`. The report space can return several rows sharing one `nodeId`, distinguished only by `userName` (several people owning one node); they are kept rather than deduplicated. `authorizationType` is `admin` or `unauthorized` and describes edit rights, not read access — unauthorized nodes still answer metric queries, so it is reported rather than used to filter. The endpoint ignores every pagination parameter, so `--page` / `--page-size` slice client-side and `total` counts the whole match set rather than the page. `--keyword` is required and must be non-blank: the platform rejects an empty term and treats a whitespace-only one as a match-all (200k rows on the employee space), so a blank one raises `DEVMIND_NODE_SEARCH_KEYWORD_MISSING` before a request goes out. Searching by node id does not work — the term is matched against names, not ids. No match is a plain empty list: unlike `report list`, this endpoint answers `[]` rather than `null` for every empty case, so a non-array response raises `DEVMIND_RESPONSE_PARSE_ERROR` instead of reading as "no nodes".
- `meta` returns `{ entries: [{ aliasId, type, displayName, description, raw }] }` for dimension/metric metadata (each id is looked up as both dimension and metric; unresolvable ids come back with `type: "unknown"` and `displayName`/`description` `null`).
- `user get` returns `{ users: [{ username, name, enName, deptName, raw }] }` for the given usernames; unknown usernames still produce an entry with `name`/`enName`/`deptName` set to `null` (empty `raw`).
- `space tree` returns `{ tree: [{ id, name, children, raw }] }` for the given space type; `id`/`name` are `null` when a node omits them. An illegal response (not an array and not a `{ data: [...] }` envelope) raises `DEVMIND_RESPONSE_PARSE_ERROR`; only `[]` and `{ data: [] }` count as a valid empty tree.
- `model list` returns `{ models, page, pageSize, total }` -- the data models behind `data_mart`, each `{ id, displayName, description, modelType, transferStatus, authorizationType, updateType, raw }` with scalar fields `null` when the platform omits them. This is where a `--model-id` for `model get` and `model partition get` comes from. The endpoint takes no parameters that do anything: page/page_size, page_num/page_count, limit, keyword, content and project_id were each probed and all returned the identical full catalog, as did a call with no query string at all, so **both filters and pagination are applied client-side** and `total` counts what survived the filters rather than the platform's catalog size. `--keyword` is a case-insensitive substring match on the display name only -- the platform's own naming mixes casing, and descriptions are empty for most of the catalog. `--status` is an exact, case-insensitive match on `transferStatus` (`ONLINE` / `DRAFT` / `DISUSE` / `OFFLINE`); non-online models still answer the other two commands, so it narrows the list rather than marking anything unusable. Display names repeat across the catalog -- dozens of models share one and differ only by id -- so rows are never deduplicated by name and the id leads the table. `authorizationType` reads `unauthorized` for the entire catalog: it gates editing, not reading, and is never used to hide rows. `modelType` is reported verbatim because the platform spells one engine several ways (`MySQL` / `MYSQL`, `ClickHouse` / `CLICKHOUSE` / `ClickHouseAuth`), which is also why it is not a closed choice list. Fields left out of the typed surface (`engine_type`, `project_ids`, `confidentiality`, `visible_space`, `last_async_time`, `access_type`, `materialized_view`) are reachable through `raw`.
- `model get` returns `{ modelId, tableName, displayName, description, owners[], createTime, updateTime, lastSyncTime, updateFrequency, status, fields, raw }` -- a model's metadata plus the physical columns of its backing table, each field being `{ dimensionId, fieldName, fieldDisplayName, dataType, caliberSql, description, raw }`. These are the table's real columns, which is a subset of what the model exposes for querying: the platform's own dimension list additionally carries virtual columns that have no physical field, including most partition dimensions, so this is the column inventory rather than the dimension inventory.
- `model partition get` returns `{ modelId, partitions }`, each partition being `{ dimensionId, maxValue, raw }` -- how recent each of the model's partitions is. `maxValue` is the latest date that partition holds data for, which is the missing half of the "a bare date query answers with an all-empty series" problem: it tells you how fresh the data is, but there is **no matching lower bound**, so it is not a queryable range. **Most models are not partitioned at all** and answer with an empty list -- that is the ordinary result, not a failed lookup, and the text output says so in words rather than printing an empty table. `dimensionId` is the partition dimension's id; resolving it to a name needs the model's dimension list, since `model get`'s field list omits most of them. An unknown model id is answered by the platform with HTTP 200 and a plain error sentence rather than data, which raises `DEVMIND_MODEL_PARTITION_FAILED`; a blank `--model-id` raises `DEVMIND_MODEL_ID_MISSING` before any request goes out.
- `model dimension list` returns `{ modelId, dimensions, page, pageSize, total }` -- everything a model can be grouped or filtered by, each `{ id, displayName, enName, description, dataType, caliberSql, ops, aggrFunctions, timeGranularities, isPartitionField, isVirtual, transferStatus, raw }`. `ops` is the point of the command: it lists the comparison operators the platform will accept for that dimension in a query filter (measured across several models: `=`, `!=`, `IN`, `NOT IN`, `>`, `>=`, `<`, `<=`, `LIKE`, `NOT LIKE`, `IS NULL`, `IS NOT NULL`, `IS EMPTY`, `IS NOT EMPTY`, `LAST`, `BETWEEN`, `SINCE`, `RECENTLYHAS`, `MAP_KEY_HAS`, `has`, `hasAll`, `hasAny` -- reported verbatim rather than validated against a fixed list), which nothing else in the CLI reports. This is a superset of `model get`'s field list -- it also carries the virtual dimensions that have no physical column, `isVirtual` marking them -- and `isPartitionField` marks the ones `model partition get` reports freshness for. The endpoint has no filtering or pagination of its own (page/page_size, page_num/page_count, limit, offset, keyword and content were each probed against a 2376-dimension model and all returned the full set), so `--keyword` and the page slice are applied client-side and `total` counts what survived the filter. `--keyword` is a case-insensitive substring matched against **both** the Chinese display name and the English one, since either may be the spelling you know. Rows are sorted by id before paging because the platform's own order is not stable between two identical calls -- without that, page 2 would be cut from a different ordering than page 1 and rows could repeat or vanish. `ops`, `aggrFunctions` and `timeGranularities` come back empty when the platform omits them, which is common: on that same model `timeGranularities` is absent from 2107 of the 2376 rows. A model id that does not exist answers with an empty list rather than an error -- the platform does not distinguish it from a model that defines nothing -- while a non-numeric one is rejected as `invalid model_id`.
- `model dimension values` returns `{ modelId, dimensionId, values, limit, truncated }` -- the distinct values one dimension holds, which is what a query filter has to be written against. `--model-id` and `--dimension-id` are both required and must belong together: a mismatched pair is answered with an HTTP 500 from the platform's backing service, not an empty list. Get the dimension id from `model dimension list`. `--keyword` is passed to the platform, which matches it as a **substring** of the value rather than a prefix, and **case-sensitively** -- unlike the client-side `--keyword` on the two list commands above, which folds case. `TOUTIAO` finds nothing where `toutiao` finds twenty. `--limit` (default 50) is a hard cut: the platform reports no remainder and no "has more" flag, so a result that fills the limit sets `truncated: true` and the text output says the list was cut, but there is no exact count of what was left behind. The limit is also enforced client-side, because the platform honours it for most dimensions and silently ignores it for some -- a virtual dimension measured here answered with all 999 of its values whatever was asked. Values are sorted ascending by code unit (the order the platform itself sends) before the cut is applied, so a given `--limit` answers with the same values every time; note that raising the limit widens the set rather than merely appending to it, because the platform samples differently per `values_num`. The empty string is kept when present: it is a real value on dimensions that are blank for some rows, and the text output labels it `(empty string)`. The platform's `db_option_num` field is deliberately not reported -- it reads like a total but is `"0"` for every single-dimension request regardless of how many values come back.
- `model metric list` returns `{ modelId, metrics, page, pageSize, total }` -- a model's metric definitions, each `{ id, displayName, enName, description, dataType, caliberSql, accumType, ops, aggrFunctions, parentId, transferStatus, raw }`. **Not the same thing as `metric list`**: that one reads the insight side and lists the business metrics published under a report node, while this reads `data_mart` and lists the physical metric definitions of one data model, which is why it lives under `model`. `caliberSql` is the aggregation each metric computes and `accumType` (`Accum` / `Unaccum`) says whether it accumulates across the time range. `parentId` points at the metric this one derives from -- the response is flat, so it is the only handle on that hierarchy. Filtering, pagination and sorting behave exactly as in `model dimension list`, and for the same reasons.
- `report list` returns `{ reports, page, pageSize, total }` — the reports (dashboards) visible to you, each `{ templateId, reportName, manager, updateTime, businessId, businessName, authorizationType, raw }` with scalar fields `null` when the platform omits them. This is where a `--template-id` for `dashboard get` comes from; without it a template id can only be copied out of the web UI. The endpoint ignores pagination and returns every row, so `--page` / `--page-size` slice client-side and `total` counts the whole set rather than the page. `--keyword` filters by report name and `--business-id` narrows to one business/space; both are optional and omitting them lists everything you can see. Fields the platform sends only for some requests (`is_official` when scoped to a business, `scene_type` / `chart_cnts` / `monitor_cnts` when not) are reachable through `raw`. A filter that matches nothing is reported as an empty list, and so is an empty array, but a `null` response to an unfiltered request raises `DEVMIND_REPORT_LIST_NO_DATA`: the endpoint answers `null` both when a filter misses and when it rejects the space/scene it is called with, and since the CLI pins that pair, an unfiltered `null` means the platform contract changed rather than that you have no reports.
- `story list` returns `{ stories, page, pageSize, total }` — the metric stories under a node, each `{ storyId, storyType, displayName, problemRegion, description, owners, modelNames, raw }`. `storyType` is `meta` for a plain metric story and `complexMeta` for a composed one. Unlike `report list`, this endpoint paginates and searches server-side, so `--page` / `--page-size` / `--keyword` are forwarded rather than applied to the response. `--space-type` selects between three distinct sets rather than filtering one (`employee` is the personal view and the largest; `report` and `business` are the tree views), and it only takes effect alongside the node path — given a node id alone the endpoint answers with the same set for every space, so `--node-path` is derived from `--node-id` via `node get` when omitted, and `DEVMIND_NODE_PATH_MISSING` is raised if it cannot be resolved. Each row also carries ~7KB of drawer state (`extra_info`, `metric_info`, `analysis_info`, `tag_config`, per-action permissions) reachable through `raw`; `model_list` arrives `null` on some rows, which reads as an empty `modelNames`. `total` is the platform's own count for the whole set, except past the end of it: there the endpoint derives the count from the page requested (page 99999 at size 3 claims 299994 rows for a set of 43667), so an empty page beyond the first reports `total: null` and prints `Stories: unknown` rather than a number that grows with `--page`. A first page that is genuinely empty still reports `0`. `--page` / `--page-size` must be positive integers: the platform does not validate them, holding the connection until the client timeout for `0` and crashing the backing service for a negative page size, so both layers reject them before sending: the flag coercion answers `Expected a positive integer` and a direct api call raises `DEVMIND_STORY_LIST_INVALID_PAGE`. A call carrying neither `--node-id` nor `--node-path` raises `DEVMIND_STORY_NODE_MISSING` (the CLI's soft-required check on `--node-id` normally reports it first). A `null` payload raises `DEVMIND_STORY_LIST_NO_DATA` — the endpoint sends a pagination envelope for every accepted request including empty ones, so a bare `null` means the request was rejected rather than that the node has no stories.
- `dashboard get` returns `{ editorId, charts: [{ chartId, chartName, groupAliasIds[], metricAliasIds[] }] }` — the charts configured on a dashboard, extracted from the editor layout. Chart definitions nested inside a layout node take precedence over that node itself, so a card wrapper carrying a title, board-level filter dimensions or a board-level metric selection is walked through to the chart inside it; a node reports itself only when nothing below it is a chart. `--template-id` alone decides which dashboard is returned (list the ids you can use with `devmind report list`); `--node-id` is required by the endpoint (it 400s with "报告id或者节点id为0" when absent) but any report node/project id you can access works and does not change the result. `chartId`/`chartName` are `null` when the platform omits them; `groupAliasIds`/`metricAliasIds` are the dimension and metric alias ids per chart (resolve them via `meta`).
- `drill dimensions` returns `{ groupDimensions, drillDimensions }` — the fields a metric can be grouped by (`group_drill_config`) and its commit-level detail columns (`drill_config`); each entry is `{ dimId, displayName, raw }` with `dimId`/`displayName` `null` when the platform omits them.
- `drill get` returns the raw drill result (`{ query_id, metric_sheet_data: { titles, series }, ... }`) for commit-level detail. When `--node-path` is omitted it is derived from `--node-id` via `node get` (the platform requires the tree path). For a composite metric (e.g. AI-contribution rate) `--alias-id` must be the metric's real `metric_alias_id`, not the metric id — omitting or mismatching it makes the platform 500 with a nil-pointer error; for an atomic metric pass `--from-type meta_metric` (alias id then equals the metric id). Discover the alias via a base `query`, and use a person dimension id for `--group-dim` (most drill scenes 500 without one). `--granularity` uses full words (`day|week|month|quarter|year`) and defaults to `quarter`; the legacy `D|W|M|Q|Y` form is rejected.
- `metric list` returns `{ metrics, page, pageSize, total }` with normalized metric summaries (`{ id, metricId, name, description, dimensions, raw }`; scalar fields are `null` when the platform omits them, and `total` is `null` when the platform omits it). When `--node-path` is omitted it is derived from `--node-id` via `node get` (the platform requires the tree path).
- `metric get` returns `{ metric }` with the same normalized shape as one `metric list` entry (`{ id, metricId, name, description, dimensions, raw }`); `raw` carries the full platform record, including the `common_dimension_list` that `query --dimensions` and `metric query --group-dim` draw on. The two flags read different fields of it: `--dimensions` matches a dimension's `display_name` (e.g. `仓库名称`, and an unknown name raises `DEVMIND_DIMENSION_NOT_FOUND` listing the available ones), while `--group-dim` takes the `id`.
- `metric query` runs the metric data query on the upgrade/query endpoint and returns the raw result. Without `--group-dim` the platform returns a trend under `chart_data`; with one or more group dimension ids it switches to the grouped `compare_analysis` scene and returns a table under `metric_sheet_data`. When `--node-path` is omitted it is derived from `--node-id` via `node get` (the platform requires the tree path). `--member` (repeat the flag or pass a comma-separated list) fills `measure_obj` under `report_tree`/`business_tree` per `--space-type`. `--granularity` uses full words (`day|week|month|quarter|year`) and defaults to `quarter`; the legacy `D|W|M|Q|Y` form is rejected. Note the three query commands are distinct: top-level `query` runs an arbitrary `data_mart/query` payload (or `--payload-file`); `metric query` is the trend/grouped view of one metric; `drill get` is commit-level detail.
- `query --dry-run` returns `{ dryRun: true, payload }`.
- `query` returns `{ result }` from the DataMind `data_mart/query` API: the grouped table under `metric_sheet_data`, or a trend under `chart_data`. This v1 endpoint returns data for the ungrouped, `person` and person-like `--dimensions` groupings; `--group-by day|week|day-person|week-person|commit` (and time or commit `--dimensions`) are accepted but answered with metadata only, which surfaces as `DEVMIND_QUERY_NO_DATA`. `--granularity` takes `day|week` and defaults to `week`; it applies only to the non-time groupings (`none`/`person`/`custom`/`commit`) — a time grouping pins its own granularity and ignores the flag — and is ignored with `--payload-file`. Use `metric query` for time-bucketed trends and `drill get` for commit-level detail.
- `builtin metric list` returns `{ metrics, dimensions }`: the curated metric_id -> name catalog and the drill-down dimension legend.
- `builtin query` returns `{ xAxis, series }` normalized from the dashboard metric-card trend (`chart_data`). `--granularity` takes `day|week|month|quarter|hour` and defaults to `day` (note this differs from `drill get` / `metric query`, which default to `quarter`, and from top-level `query`, which defaults to `week`). The two sides are positional: `xAxis[i]` labels `series[].data[i]`, and every element of the platform's response keeps its slot even when it is unreadable, so an axis point that cannot be read is labelled `#<index>` rather than dropped (treat a `#`-prefixed label as "no timestamp reported", not as data). An unreadable data point reads as `""`. Values are decimal-fraction strings, not percentages: a rate metric reads `"0.9459459459459459"`, an exact zero reads `"0"`, and a bucket the platform has no data for reads `""`. A range the account has no data in at all comes back as a single sentinel point labelled `0001-01-01` with an empty value.
- `builtin tool-ratio list` returns `[{ metricId, name, value }]` — the last non-empty, non-zero value per curated metric, taken from the metric's own (first) series; `value` is `""` when every bucket is empty or zero, so an all-zero metric is reported as blank rather than as `"0"`. `--granularity` defaults to `day` as in `builtin query`. Per-metric failures surface as `ERR <message>` rows instead of aborting the batch, but an auth failure is not per-metric and aborts with `DEVMIND_AUTH_FAILED` (or `DEVMIND_AUTH_JWT_MISSING` / `DEVMIND_AUTH_USERNAME_MISSING`) and a non-zero exit — otherwise a dead credential would report every metric as an `ERR` row under a success envelope, which a script cannot tell apart from real data.

The CLI unwraps platform envelopes and does not expose raw `errno` success wrappers.
