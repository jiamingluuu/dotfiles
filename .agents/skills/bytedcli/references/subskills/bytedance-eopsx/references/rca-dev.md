# EOpsX DevKit：本地文件开发，远端草稿执行

仅在归因 Skill 开发、草稿管理、远端验证和调试时使用本指南。普通告警、元数据、BCP、风险或 guard 查询沿用主 Skill 的平台指引，不套用开发状态格式。

## 开始前：工具与创作能力

- 先用 `bytedcli eopsx dev --help` 确认本地版本支持开发命令；CLI 名称始终是 `bytedcli eopsx dev`。登录先查 `bytedcli auth status`，网络失败或空间拒绝访问不等于未登录。
- 内容创作可配合独立提供的 `eopsx-rca-skill-creator`，平台交互由当前 `bytedance-eopsx` 负责。Creator 不随 bytedcli 分发，不能用 `bytedcli self skill install` 安装它。已有安装或用户提供完整本地目录时，先读取实际 `SKILL.md` 及所需引用，再使用；缺少时询问该目录或请维护者提供，不编造下载地址，也不声称已加载。
- Creator 缺失不阻塞已有 Skill 的参考下载、草稿上传和测试；用户需要创作方法时可以先整理材料或跳转网页共创，不能假装执行了 Creator 流程。

## 工作边界

用户在普通文件夹中开发。本工具通过已有 SSO 身份操作空间草稿，不需要用户理解内容仓库。不创建空间，不做 Git、Snapshot、本地 Runtime、A2A/SSE、批量跑测或本地发布。圈选告警、跑批、最终发布返回网页链接，由用户在网页操作。

同一个开发目录共享一个当前远端 Session；不是每个 Codex/Trae 窗口各有一份。状态由 CLI 管理，对用户称“当前项目状态”，不要要求用户手改内部文件。

## 交互展示（每轮正式回答）

正式回答先按骨架填写，不先自由回答再追加状态；与 Creator 同时使用只输出一套。短问句“测完了吗”“为什么”“继续”仍属于当前开发流程，用户明确切换无关话题时才退出。以下是结构，不输出外层代码围栏或占位符：

```markdown
### 当前进度

<阶段> · <已知空间> · <当前 Skill>
本地改动：<逐项写新增/修改/本地删除的 Skill 名称及各自草稿保存状态>。
测试：<未开始/等待确认/正在执行/已结束/状态未确认；涉及测试时列告警或问句、完整草稿组合，临时启用的正式 Skill 单列>。

### 这次做了什么

<仅本轮真实动作；只讨论就写未修改、未上传、未发起测试>。

### 结果

<直接回答本轮问题；返回了远端正文就在此完整展示，再附证据链接、可用的任务/会话/Trace 标识及限制>。

### 接下来

<符合当前阶段的推荐动作、可直接说的话或复制的命令；有待确认操作就说明对象和影响并提问>。
```

每轮正式回答固定四个独立标题，顺序为「当前进度 → 这次做了什么 → 结果 → 接下来」，不得合并或省略。初始化、澄清、解释已有 Skill、修改、上传预览、等待确认、测试中、失败与无操作的回复均适用；短回复每段一句即可。工具执行过程中的简短进度消息不必重复整块，但本轮正式回答必须完整。CLI JSON 或终端摘要不是最终答复模板，AI 要把真实数据组织成四段。

CLI 负责返回状态、结果、错误、标识和页面链接，以及执行必要的确认与并发保护；本指南负责回复格式、用户引导和下一步选择。不要等待 CLI 返回 `next_steps` 或交互话术，也不要把工具中的普通错误修复提示当作新的用户授权。

- **当前进度**：空间、正在开发的 Skill，以及本地修改涉及的名称（新增/修改/本地删除）和各自上传情况。依据本轮实际文件修改和当前项目状态；需要核对已知工作包时，使用不带 `--yes` 的上传预览，将 content_hash 与同空间、同路径的成功上传记录比较。不为展示触发上传或全空间下载。旧记录缺失就标「未确认」，新包无成功上传记录标「尚未上传」。本地删除不等于远端删除。
- **当前进度中的测试信息**：发起、查进度、展示结果时，明确测试告警或问句摘要、真实执行状态、**本次完整草稿名称列表**（空则写「未选择草稿」）；临时启用的正式 Skill 单独列出。选择不等于模型实际调用，本地尚未上传的改动不自动参与测试。
- **这次做了什么**：只写本轮实际动作；仅讨论就说明未修改、未提交、未测试，不编造操作。
- **结果**：直接回答本轮问题，放真实结果与待确认项；本地已修改、草稿已保存、测试已受理、测试已结束、正式已发布分别说明，不相互替代。远端正文放在这一段，不能为了保持简短而省略。
- **接下来**：给用户可直接说的自然语言。测试开始后提示查进度、停止并 reset/换告警；测试结束后提示追问调试、reset 或换告警。具体边界见下文，不只给 task_id 或网页链接。

发送前检查四段是否齐全、本地改动名称与上传/测试状态是否有依据，以及下一步是否符合当前状态。未知写未确认，不为填模板额外上传或启动测试。

## 完整对话示例

以下是交互示范，不是当前用户的执行记录。名称、链接、ID、文件范围和状态都换成真实值；获取不到就说明缺失，不照抄示例数据。链接中的 example.com 仅为示例。保持四段结构，但不输出包住整份示例的代码围栏。不要照抄下面全部场景，只按本轮实际状态回应；不为了复现示例而运行命令。

```markdown
检查了工作包并生成上传预览；没有实际上传。

不会发布正式 Skill，也不会修改正式开关。保存草稿本身不会自动开始测试。

### 接下来

确认把这个完整包保存到该空间的 demo-rca 草稿吗？你可以说：「确认保存草稿」。
```

### 草稿已保存：展示三种验证方式

用户已确认上传；已知：`demo-rca`、`demo-evidence` 两个包都保存成功，当前本地内容与成功上传记录一致；未开始测试，机器人是否绑定未知。

````markdown
### 当前进度

待验证 · 示例空间

### 这次做了什么

### 结果

```text

等机器人确认草稿选择后，再发送要排查的告警。这些入口的会话和选择不会自动互通。
````

```markdown
### 这次做了什么

### 结果

还没有结束，当前状态是 running，暂时没有最终结论。

### 接下来

```

### 测试完成：正文直接展示，不只给结果文件

用户：「测完了吗？」已知：原任务 `succeeded`，`finish_reason=stop`；示例远端完整正文只有下列三句，并未确认根因。实际更长的正文同样完整展示，不按示例长度截断。Session、Task、Trace 均使用真实回执值；没有的字段说明缺失，不编造。

```markdown
### 当前进度

远端测试已结束 · 示例空间 · event_id:1111
本次草稿：demo-rca、demo-evidence；未临时启用正式 Skill。本地本轮无修改。

### 这次做了什么

> 当前证据不足以确认根因。
> 报警窗口内请求失败上升，但缺少同窗口的错误日志，尚不能判断由哪个环节引起。
> 建议补充该窗口的错误日志后继续确认。

本轮解析的草稿选择为 demo-rca、demo-evidence；这不证明模型实际调用了它们。
会话：demo-session；任务：demo-task；Trace：demo-trace。
任务执行结束不代表排查结论已经达到验收要求。

### 接下来

要继续调试，你想选择「询问原远端 Session」还是「通过 Fornax 查看调用过程」？我不会默认进入任一种。
也可以说：「重置对话重新测这条告警」或「换个告警测试」。如果你确认效果满足要求，可以说：「带我去网页发布」；发布由你在平台完成。
```

## 从需求到文件

1. 首次先检查 `bytedcli auth status`；只有明确身份异常才引导 `bytedcli auth login`。网络不可达、无空间权限不等于没登录。
2. 用户已选空间：`bytedcli --json eopsx dev init --space-id <id>`，展示后确认加 `--yes`。不强制下载。
3. 用户要开发新 Skill 且尚无材料：主动用 `bytedcli --json eopsx dev web` 获取已绑定空间的真实页面链接，引导在网页圈选告警并复制素材回来。不要等用户追问“怎么圈选”，也不要仅回复五步开发概览或“请给一条报警/SOP”。尚未绑定先完成绑定，再接着给圈选入口；已有材料、SOP 或明确修改目标就直接接手，不强迫重新圈选。
4. 告诉用户具体操作：打开空间的 Skill 页 → 点击「智能共创」→ 在第一步「圈选告警样本」设置筛选并查询 → 勾选同一业务场景下有代表性的告警 → 点击「查询」旁的「复制圈选素材」→ 粘贴回当前聊天。说明收到素材后先梳理业务链路、确认排查思路，再写到本地；仅在已核对并读取 Creator 时，才承诺使用 Creator 辅助。此时只获取材料，不要求用户继续在线上生成、发布或跑批；不把返回页面链接说成已打开弹窗或已选告警。
5. 按需问用户是否参考线上 Skill 或已有目录。需要参考时先 list，确认来源空间与准确 ID，再 download；下载使用刷新，不靠正文 version 判断版本。不把下载全空间 Skill 或先命名/建目录作为圈选前提。
6. 创作内容按“开始前”核对并读取另行提供的 Creator；它写用户指定的工作目录，不能修改 online reference。缺少 Creator 时如实说明，接受用户已有 Skill 或先去网页共创，不执行无效的内置安装命令。

首次引导仍按四段回复：`当前进度` 说明空间与待圈选、尚未创建 Skill；`这次做了什么` 只说明实际获取了网页入口；`结果` 放工具返回的可点击真实链接，说明尚未圈选或执行开发；`接下来` 给上述点击路径，并告诉用户「选好后把复制的素材直接粘贴到这里，我会结合这些真实告警和你提供的业务资料，先与你确认排查思路，再开发 Skill」。链接获取失败就报告限制，不编造 URL；用户没有可圈选的告警或不方便使用网页时，接受已有 SOP、历史故障材料或口述需求，不阻塞开发。

```bash
bytedcli --json eopsx dev skills list --space-id <id> --page 1 --page-size 20
bytedcli --json eopsx dev skills download --space-id <id> --skill-id <skill-id> --editable-dir ./skills/my-skill
# 用户确认后才追加 --yes
```

每次实际参考线上对象前检查对应在线包；一致则复用参考，变化则提示并在确认后刷新，不必下载全空间。默认参考位于当前项目状态区；可用 init 的 `--reference-dir` 指定。下载参考按内容仓库的 common/<Skill名>、eops/<Skill名>、customization/<空间名>/skills/<Skill名> 或 skills-develop/<Skill名> 组织；这是参考目录，不要求用户管理 Git。引用下载返回的路径，不猜目录名。旧 ID 目录保留，下一次确认下载会写入可读路径，不自动清理旧文件；本地改过的参考仍禁止覆盖。只读参考要改时复制到独立工作目录；官方/内置内容不能改造成同名业务草稿，但可以参考写新的业务 Skill。

平台的列表/空间元信息暂时不可读，但按 ID 下载仍被允许时，工具会降级到参考根目录下的 `<来源空间ID>/<Skill名>`，返回 `reference_layout=space-name` 和 `reference_warning`。向用户说明当前只能使用简化布局，不声称已按仓库结构归类；不因此要求重新登录或扩大权限。下载接口本身拒绝则仍报错，不绕过权限。下载预览为确定准确名称会读取元信息和 ZIP，但不写本地文件；确认后才保存参考副本。

## 保存草稿与测试

开发顺序是：**本地开发 → 保存为空间草稿 → 选择本次草稿组合 → 验证 → 调试改进或网页发布**。保存不是验证，验证也不是发布。

草稿保存成功后，按下表向用户说明三种验证方式（用户已指定其中一种则优先按其意图，其余简短列为可选）。网页链接使用上传回执的 `web_url`，或通过 `dev web` 获取，不依赖 CLI 返回流程话术：

| 验证方式 | 用户可以怎么说 / 怎么操作 |
| --- | --- |
| 本地 AI 助手调用远端 | 「用 A、B 草稿测试 event_id:1111」。确认完整草稿组合后 `chat submit` 新建远端 Session，结果回到当前聊天。 |
| 网页共创 / 跑批 | 「去网页共创验证这批草稿」。用 `dev web` 返回真实空间 Skill 页，用户点击共创、选草稿和告警样本再测试；批量评测也在网页操作。不要声称链接已打开共创或自动选好草稿。 |
| 飞书机器人（如该空间已绑定） | 在对应机器人会话发送 `/test-skill A B`（实际草稿名称，空格分隔），等选择成功后发「排查 event_id:1111」；`/test-skill` 查看当前选择，`/test-skill off` 退出。没有机器人不要求用户专门配置，可直接选前两种。 |

三种入口都要明确**本次完整选择**，不会自动包含全部草稿，也不会同步其他入口的 Session 或选择。机器人选择仅影响相应测试会话，不改正式开关。只知道 space_id 并不能证明该空间已绑定机器人，未知时用条件说明，不编造机器人链接。本地 CLI 使用逗号分隔的 `--drafts A,B`，机器人使用空格分隔的 `/test-skill A B`，不能混用。

上传后可这样交付：「这批草稿已保存，尚未开始验证。你可以：①直接给我告警 ID，用这些草稿远端测试；②打开这个空间页面，点击共创验证或跑批；③如已绑定机器人，复制下面的命令选择草稿，等选择成功后再给它告警。你想先用哪一种？」如果用户已经明确选择并确认了测试，不重复询问路径，但仍核对实际保存结果与本次完整选择。

**复制即用的交付规则。** 对需要用户操作的机器人/终端命令，在独立代码块里填好实际名称、ID 或路径，不只给语法模板。块内只放命令，不混入序号、解释、提示符或“替换成你的名称”；参数未明确则先询问，不能把占位值说成可直接执行。机器人命令用 `text`，终端命令用 `bash`；不同发送位置、需要等待回执的下一步和退出操作各自分块。AI 已在代用户操作的 CLI 不必让用户重复执行。

例如本次已确认的草稿名是 `demo-rca` 和 `demo-evidence`，告诉用户「复制下面这一条，发给该空间的飞书机器人，不是在终端执行」：

```text
/test-skill demo-rca demo-evidence
```

实际交付时替换成**本次完整选择的真实草稿名**，空格分隔；名称含空格时使用英文引号，不能直接照抄示例。收到「已开启草稿测试」及本次名称、Session 后，再提示发送用户给定的告警。不能把发出命令视为已经启用；没有真实告警 ID 就请用户提供，不编造。

需要核对机器人当前选择时，单独给出：

```text
/test-skill
```

用户要退出草稿测试时，再单独给出以下命令并说明会开始普通会话；仍在执行要先停止并确认结束：

```text
/test-skill off
```

收到 `Unknown command /test-dev` 时，说明本期命令是 `/test-skill`，不是 `/test-dev`，不要建议去掉斜杠让模型猜。若准确的 `/test-skill` 也返回 Unknown command，才提示维护方核对该机器人实际连接的 Agent 是否加载本期 overlay；不能仅凭 `/test-dev` 的错误断言部署失败。该错误尚未进入草稿名称/权限校验，更不代表草稿已生效。

```bash
bytedcli --json eopsx dev skills upload --skill-path ./skills/my-skill
bytedcli --json eopsx dev chat submit --drafts skill-a,skill-b --message '请排查 event_id:1111'
bytedcli --json eopsx dev chat status
bytedcli --json eopsx dev chat ask --message '请根据刚才会话已有的执行记录解释：为什么没有调用 skill-a？不要主动重新排查告警。'
bytedcli --json eopsx dev chat stop
bytedcli --json eopsx dev web
```

上述写动作首先不加 `--yes`，展示空间、包文件范围/摘要、完整草稿选择或当前 Session 后，请用户确认才执行。用户只说“看看怎么做”不算授权。上传是替换同空间共享草稿的完整包，删除附件也会生效；不修改正式内容和开关。上传只报告真实保存结果，不把“已上传”说成“已加载”。

`chat submit` 的 `--drafts` 是本次完整草稿名称列表；`--enable-skill-ids` 是临时启用的正式对象 ID 列表，二者不能混用。正式临时启用不修改全局开关。缺省列表是空选择，不自动加入所有草稿。

本地文件修改后要先上传为空间草稿才测试。收到“测试当前最新修改”时检查上传预览/成功记录，不跳过上传直接声称远端用了当前文件。上传后参考刷新失败，只补 download，绝不自动重传草稿。

## 测试、查询和调试意图区分

本地测试受理后就告诉用户：「远端正在处理，请等待；稍后问我『测完了吗』即可查看结果。也可以停止本次测试。」不阻塞等待归因完成、不承诺后台推送。用户再次问进度时只查原任务，结束则直接展示真实正文；随后提供原 Session / Fornax 两种调试路径，以及「验证没问题了，带我去网页发布」。失败或中断也要直接展示已返回内容和限制，不能建议当作验证通过直接上线。

依据 `execution_status` 区分：`accepted/preparing` 是已受理或准备中，不代表已经开始归因；`running` 才是执行中；`stopping` 是尚未停止；`unknown` 是无法确认，不得说成「仍在执行」或「已停止」。状态未知时先查询原任务，不重发；`failed/stopped` 不是验证通过，不给直接上线的推荐。

| 用户说                                  | 动作                                   | 明确告诉用户                                                           |
| --------------------------------------- | -------------------------------------- | ---------------------------------------------------------------------- |
| “用 A、B 草稿测试这个告警”              | 先确认已保存，chat submit              | 新 Session，完整选择；立即返回 task_id，不等十分钟                     |
| “刚才查完了吗”                          | chat status 一次                       | 仅查询原 task，不启动归因；结果已返回则直接展示正文，不自行长轮询      |
| “刚才为什么没调用 A / 帮我调试这次结果” | 先询问调试方式                         | 选择「询问原 Session」或「Fornax Trace 排查」，未选择前不执行任一方式  |
| “直接问刚才的远端会话，日志结果是什么”  | chat ask                               | 明确选择后继续原 Session；新 Turn 有新 task_id，自动带回原完整草稿选择 |
| “用 Fornax 查这次调用过程”              | 使用可用的 fornax-cli 指南查对应 Trace | 用户已指定方式，不再次询问；Trace 不等于完整 Session 历史              |

用户只是问本地已返回的结论，优先直接解释已有结果。需要补充执行证据且未指定调试方式时，先让用户选：原 Session 依据已有历史回答，或 Fornax 查看调用链/工具输入输出。原 Session 不可用或 Trace 缺失时说明情况，再请用户决定是否换方式，不自动切换。询问原 Session 是一次新 Turn，不是 inspect，也不是读取 SessionDB 的新接口；历史丢失就如实说明，不静默重新归因。

恢复测试上下文时，使用工具返回的 test_context.initial_message（原测试问题）、user_content（本轮问题）和 drafts（本次草稿）。提交预览的 current_test 表示之前的任务，不能与预览的新测试混淆。旧项目可能没保存问句：先查当前对话先前的提交回执，不因缺少问句就建议停止重测，更不能编造告警 ID。相同告警可能是查进度，也可能明确要求重测，根据用户意图区分。

修改草稿、换告警默认新测：submit 创建新 Session。仍在执行则先 stop，确认真正 stopped/succeeded/failed 后才能启动下一次。stopping/unknown 都不能当成停止完成。停止不会撤销 Tool 已做的外部操作。

**reset 是交互意图，不是独立 CLI 命令。** 用户说「重置这次对话」：说明下一次测试会用新 Session；如果当前仍在执行，先确认停止。告警和完整草稿选择明确后用 chat submit 发起新会话，不延续旧会话。只说 reset、没给下一条输入时，问要测哪个告警，不虚报已创建空会话，不删除本地状态、草稿或结果。用户明确要追问旧 Session 时仍可以使用其已知 ID。

测试结束后可提示：「可以直接问刚才的远端会话，为什么没有调用 A；也可以选择 Fornax 排查。还可以说『换个告警测试』或『重置对话，重新测这条告警』。」运行中对应提示先查进度或确认停止，不暗示支持并行执行。

受理未知且没有 task_id 时不要自动重试，也不要删除本地状态绕过限制；相同 session_id 不是幂等键。已拿 task_id 就查询原请求。平台确实拒绝或身份失败应显示原错误，不编造执行结果。

首次提交回执的 requested_session_id 只是客户端提示，不是远端真实会话 ID；首次 status 返回实际 session_id 后工具才记录用于续聊。不要拿提示值直接追问。

结果保留真实 session_id、task_id、trace_id（可能没有）、finish_reason 与 effective_skills。effective_skills 只说明本轮解析选择，不证明模型实际调用。截断/失败/中断不说成归因成功。

**只保留原归因 Trace 和最近一份完整回复，不逐轮归档。** `attribution_trace_id` 指首次测试的归因 Trace；`result.trace_id` 属于当前返回的这一轮，追问后可能不同。查原告警归因时用前者，查刚才的追问执行时用后者，不能混用；旧状态没有原归因 Trace 就说明未记录，不拿追问 Trace 冒充。`.eopsx/results/latest.json` 固定保存当前任务实际返回的终态正文及其 task/session/Trace，下一份终态正文覆盖它。追问等待、无正文或查询失败不会清空上一份回答；读取缓存先核对文件中的 task/session 和问题，不把上一轮回答说成本轮结果。显式查询旧任务只交付本次返回内容，不覆盖当前结果；旧版本已有结果文件保留，不自动清理，也不额外创建逐轮 Markdown/JSON。

**结果交付必须在当前聊天完成。** 收到 result.content 后直接展示返回正文，保留根因、影响范围、证据及链接、待确认项；可以调整排版，不能只给一句摘要或 result_path 让用户自己打开。长结果按段展示，不默默省略；工具输出被截断时先读取返回的本地结果文件再展示。结果文件是辅助留档，不是用户必须打开的文档。远端追问回答同样处理；失败/中断附已有内容和限制，成功但无正文就明确无正文。查询网络失败表示「暂时查不到状态」，保留最后已知状态，不能宣称归因失败或重发任务。

## 空间变化与本地参考更新

每轮进入本开发流程或配合 Creator、且涉及已选开发空间的操作，做一次检查：init 关联空间后、继续开发/需要线上参考、保存前、验证前、查询结果/调试或跳转发布时。同一用户轮次复用刚查到的结果，不在每个工具调用前重复查，不做后台定时或轮询。尚未选空间的纯离线编辑不强求联网。

```bash
bytedcli --json eopsx dev skills diagnose
# 检查其他来源空间（仅在权限范围内）
bytedcli --json eopsx dev skills diagnose --space-id <source-space-id>
# 验证前核对所选草稿：读真实 ZIP，不写缓存或工作文件
bytedcli --json eopsx dev skills download --skill-id <draft-id>
```

`diagnose` 分页读取空间可见 Skill 清单，只记录检查结果，不下载或覆盖包。`space_changes` 给出新增、变化、不再可见的名称；`cached_references.status=possibly_outdated` 表示缓存对应列表信息变了，`unknown` 表示旧缓存没有比较依据。发现变化时提示：「你的空间 Skill 有更新，A 的本地参考可能落后，要检查并更新缓存吗？工作文件不会被覆盖。」用户暂不更新，下次相关交互仍可提醒未同步参考，不打断同一轮。

- 首次 `baseline_created` 只能说建立清单；`uncached_skills` 是尚未缓存，不能说成全部刚刚新增。
- `no_metadata_change` 不是包内容完全一致：列表没有包哈希，更新时间不一定覆盖附件变化。**三种验证入口在引导开始前，对本次所选草稿按准确 ID 做 download 预览**，比较 `content_hash` 与本地参考/成功上传记录；附件也计入摘要。`content_changed=true` 表示与缓存记录的实际内容差异，`null` 表示没有缓存基线。不要只看正文 version。
- 所选草稿与本地参考/成功上传内容不同，先显示名称和差异，请用户检查：更新参考并确认用远端当前草稿测试，或保留工作文件并重新预览上传。不自动覆盖共享草稿，不因更新缓存就上传工作包。没本地副本就说明使用远端草稿，不说本地落后。
- 确认更新后针对相关 ID 执行 download `--yes`，只更新工具管理的参考区；可另选缓存目录。工作文件不自动合并/覆盖；手改的参考按现有保护停止覆盖。开发时再按需吸收变化。
- `check_status=unavailable`、分页不完整、权限失败：明确「暂时无法确认版本」，保留原缓存，不当成最新或全被删除。`no_longer_visible` 可能是删除或可见性变化，不擅自删本地文件。旧 CLI 没有 diagnose 时说明需更新工具，不伪造检查成功。
- 用户问「测完了吗」，优先查询并交付测试结果，再附更新提醒；检查失败不隐藏结果、不重发任务。更新缓存不改变正在执行/已完成的 Session；追问原会话仍针对原执行。

检查范围是空间 **Skill 清单与相关参考包**，不是 Agent 配置、容器或 DevKit 安装版本。检查与执行间没有版本锁，实际使用内容以远端回执为准。网页/机器人里稍后才开始测试，本地不能代替那一刻的平台校验。

## 网页入口

`dev web` 返回空间 Skill 页；有既有批次可加 `--eval-batch-id`。告诉用户在网页圈选告警并复制素材到本地；本地不写第二套圈选或跑批工具。最终发布永远跳网页，核对实际草稿及正式覆盖目标。

## 本地目录（工具维护）

- 用户工作目录：可编辑的完整 Skill 包与独立开发素材。
- `.eopsx/project.json`：空间、参考目录、来源关联、成功上传摘要、可选的 `space_observations`（最近一次清单观察）；参考记录增加可选的 `remote_metadata`。旧记录仍兼容，没有比较依据就标未知；不存 Token。
- `.eopsx/session.json`：当前 Session/task/完整选择/状态、原测试问句 initial_message、本轮问句 user_content；attribution_task_id / attribution_trace_id 保留首次归因标识，result_path / result_task_id 指明已保存回复属于哪一轮。少量 recent 只保留会话定位信息，不为每个会话归档正文；旧记录缺字段仍可使用，不手工补造。
- `.eopsx/online-skills/`：线上只读参考；本地手改时停止覆盖，保留文件后换参考目录。
- `.eopsx/results/latest.json`：当前开发目录最近一份终态回答，覆盖更新，不是远端原始记录或历史库。切换新会话等待期间，文件可能还是上一会话的结果；以文件内标识为准。旧版本结果文件不自动删除。

选择别的开发目录用各命令 `--directory`；不要为一次 AI 对话另建 project/session 状态。
