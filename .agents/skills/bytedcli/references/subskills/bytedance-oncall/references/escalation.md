# Oncall 故障排查与升级

**开始前先确认已读取公共技能 `bytedcli`，再运行 `bytedcli oncall --help` 确认当前命令面。**

执行“补齐问题 → 选择租户与分类 → 创建追踪工单 → 自助排查 → 分类处理 → 必要时确认建群”的标准流程。除缺少关键信息、等待扩大搜索授权或最终建群确认外，不中途等待用户选择。

## 进入条件

- 仅处理具有明确 Oncall 意图的具体故障，例如“用 Oncall 排查”“提单”“P0 提单”“发起 Oncall”或“建 Oncall 群”。普通排障先交给对应领域能力；单纯查询已有数据使用主技能中的查询路由。
- `trigger_message` 至少包含故障现象、报错、操作目标或影响范围；空泛求助时只补问该字段。
- 用户未指定等级时使用 `P2`。P0 必须补齐在线影响和事故范围 `urgent_description`，并跳过自助排查。
- 用户表示已解决、取消或停止时，立即结束。

## 按阶段读取

| 阶段 | 读取 | 完成条件 |
|---|---|---|
| 1. 定位与追踪 | [问题补齐、租户分类与追踪工单](intake-and-routing.md) | 保存当前 `oncall_flow_id`、租户、区域、分类、`type_action` 和选择依据 |
| 2. 自助排查 | [自助排查与证据归类](self-help.md) | P1/P2 的五项能力都有最终状态，或达到高置信停止条件；P0 跳过 |
| 3. 分类与升级 | [分类处理、最终确认与发起群聊](classification-and-launch.md) | 按服务端分类结束，或经用户最终确认后成功建群 |

## 全局门禁

1. 自主选择最匹配的租户、区域和分类并记录依据；不要让用户逐项选择。
2. `flow create` 只创建内部追踪工单，不代表“已发起 Oncall”。`terminal=false` 和 `oncall_launched=false` 表示流程未完成。
3. P1/P2 任一可靠证据使解决置信度达到至少 90% 时，立即展示依据和步骤并停止升级准备；不要等待其他并行项，也不要声称未经用户执行的操作已经恢复业务。
4. 只有服务端分类要求 `create_chat`、未达到高置信停止条件且用户最终明确同意升级后，才能携带 `--confirm` 执行 `chat create`。
5. 最终建群必须使用当前流程最近一次成功 `flow create` 返回的 `oncall_flow_id`；不得误用历史工单 ID。
6. 服务端返回的链接、目标群、目标租户和分类动作必须原样使用；缺失时说明原因，不要猜测。

## 会话状态

持续维护：问题描述与等级、租户/区域/分类及依据、租户能力开关、分类动作和后续处理信息、当前 `oncall_flow_id`、五项自助排查状态、六类资料、解决置信度及依据、`self_help_summary`。

等待字段时，将用户下一轮回复优先补入该字段。高置信停止后用户回复“继续升级”或反馈方案无效时，从未完成或已取消的自助项恢复；恢复不等于已获准建群，仍须执行最终确认门禁。
