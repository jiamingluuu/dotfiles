# 客户端 MR 覆盖率检查报告模板

本文档用于统一记录客户端 BITS MR 的覆盖率检查结果。报告必须区分远端覆盖事实与人工推断，不能把“未覆盖”直接等同于“漏测”。默认只读检查；任何标签、评论或其他写入都需要人工确认。

## 使用边界

- 输入优先使用客户端 BITS MR 覆盖率详情页的完整 URL。
- 覆盖率接口只证明某行是否被采集命中，不能单独证明业务是否漏测、无法测试或无法插桩。
- 分类前应尽量补充 MR diff、本地相关代码、模块文档、已有测试、MR 描述、评论和检查项。
- 本地工作区存在未提交改动时，必须说明是否与目标文件相关，不能混入 MR 结论。
- 证据不足的行保持“待确认”，不得为了完成报告强行分类。
- 报告生成和分类分析不授权执行 BITS 写接口。

### 2. 覆盖率概览

| 指标                 |       数值 |
| -------------------- | ---------: |
| 覆盖率文件总数       |      `<N>` |
| 存在待处理行的文件数 |      `<N>` |
| 有效变更行           |      `<N>` |
| 已覆盖行             |      `<N>` |
| 未覆盖行             |      `<N>` |
| 行覆盖率             | `<NN.NN%>` |
| 已有标记行           |      `<N>` |
| 待标注行             |      `<N>` |
| 其他非待处理未覆盖行 |      `<N>` |
| 拉取失败文件         |      `<N>` |

计算口径：

- `行覆盖率 = 已覆盖行 / 有效变更行`。
- `其他非待处理未覆盖行 = 未覆盖行 - 已有标记行 - 待标注行`，包括不可评论或没有有效行号的未覆盖行。
- 拉取失败不应静默忽略，应在结论中单独说明其影响。

### 3. 证据清单

| 证据                     | 状态                               | 用途或限制             |
| ------------------------ | ---------------------------------- | ---------------------- |
| BITS 文件树与行级源码    | `<已读取/失败>`                    | 确认远端覆盖事实       |
| MR 元数据与 diff         | `<已读取/缺失>`                    | 判断变更目的和控制流   |
| 本地相关代码             | `<已核对/无本地仓库/存在冲突改动>` | 补充完整上下文         |
| 模块文档、技术方案或协议 | `<已读取/未找到>`                  | 确认稳定业务约束       |
| 已有测试与本次测试改动   | `<已读取/未找到>`                  | 判断是否已有 Case      |
| MR 描述、评论与检查项    | `<已读取/未读取>`                  | 查找测试证据和已知风险 |

### 4. 分类汇总

本节只分类远端报告提供行级明细的“待标注行”。已有标记行和其他非待处理未覆盖行不进入分类，分别使用覆盖率概览中的统计说明。

| 建议分类           |  行数 | 判断依据                                             | 是否需人工确认 |
| ------------------ | ----: | ---------------------------------------------------- | -------------- |
| `miss-test`        | `<N>` | 业务或防御分支可稳定构造，但现有测试/采集未命中      | 是             |
| `untestable`       | `<N>` | 强依赖外部环境、系统时序或不可稳定控制的状态         | 是             |
| `uninstrumentable` | `<N>` | 控制流证明必经，但仅孤立语句未命中，存在明确插桩偏差 | 是             |
| `useless-code`     | `<N>` | 有充分证据证明不可达、重复或已失去业务作用           | 是             |
| 待确认             | `<N>` | 缺少 diff、方案、Case 或运行证据                     | 是             |

分类原则：

- `miss-test`：必须能描述可复现的输入、路径与预期结果。
- `untestable`：需要说明不可稳定测试的具体限制，不能只写“测试困难”。
- `uninstrumentable`：需要相邻覆盖行或控制流证据，不能仅凭单行 `return`、赋值或括号猜测。
- `useless-code`：结论应能支持后续删除或简化；无法证明时保持待确认。
- 连续代码行属于同一业务路径时按路径归类，避免把每个语法行误当成独立 Case。

### 5. 文件与行级结论

| 文件             | 未覆盖行  | 路径或场景             | 建议分类      | 置信度       | 依据                             | 后续动作                      |
| ---------------- | --------- | ---------------------- | ------------- | ------------ | -------------------------------- | ----------------------------- |
| `<path/to/file>` | `<10-18>` | `<业务分支或防御场景>` | `<miss-test>` | `<高/中/低>` | `<diff、文档、测试或控制流证据>` | `<补 Case/人工确认/检查插桩>` |

填写要求：

- 行号使用远端覆盖报告对应的目标提交行号。
- 同一路径的连续行合并记录；不同触发条件必须拆开。
- “依据”应写事实，不写“看起来”“应该是”等无证据判断。
- 低置信度结论不得直接进入写入清单。

### 6. 待补 Case 清单

| Case ID  | 目标路径           | 前置条件               | 操作或输入           | 预期结果                 | 建议层级              | 关联文件与行  | 优先级       |
| -------- | ------------------ | ---------------------- | -------------------- | ------------------------ | --------------------- | ------------- | ------------ |
| `CC-001` | `<待覆盖业务路径>` | `<账号/配置/页面状态>` | `<可复现步骤或入参>` | `<业务结果、状态或埋点>` | `<单元/集成/UI/人工>` | `<file:line>` | `<P0/P1/P2>` |

Case 清单只收录建议为 `miss-test` 且能够明确复现的路径。`untestable` 和 `uninstrumentable` 不应伪装成普通测试 Case；如需工程化验证，应单独记录依赖的测试钩子或插桩修复。

## 提交前自检

- 覆盖统计可以相互校验，比例计算正确。
- 所有待标注行都进入了分类或“待确认”，数量之和等于待标注行总数。
- 未覆盖行可以拆分为已有标记、待标注和其他非待处理三类，统计能够相互校验。
- 每个 `miss-test` 分类都能映射到独立 Case。
- 没有仅凭单行代码推断业务意图。
- 明确记录了拉取失败、缺失证据和本地脏工作区影响。
- 没有在未确认时调用评论或标签写接口。
- 报告未包含真实 token、Cookie、临时认证参数或其他敏感信息。
