# BABI Bill 业务排障

通用安装、认证、JWT、网络和更新问题先按入口 SKILL 指定的公共/产品 skill 处理。

## 主体解析停住

**现象：** 用户已经给出业务名，Agent 却因“没有历史记忆”“没有账号 ID”再次要求提供业务名、账号名或 ID，或先问是否执行名称搜索。

账单查询需要稳定主体 ID，但名称到 ID 的查询应由 Agent 完成；没有历史记忆不影响按当前请求中的名称搜索。按以下顺序恢复：

1. 从当前请求及对话中复用已有名称，按[账单编排](workflows.md#先定位对象再查询账单)加载对应资源指南。BABI 账号名交给 [babi-account 指南](../../babi-account/GUIDE.md)，例如业务名为 `demo-storage` 时执行 `bytedcli babi account list --fuzzy-name demo-storage --limit 100`；不要再次索要同一个名称或先问是否搜索。只有普通业务名、主体类型未明确时，还需解析服务树候选，不能仅凭账号有结果就认定主体。
2. 根据实际搜索结果处理：唯一、类型明确且精确匹配的候选可继续；多个候选或账号与服务树同时命中时，展示稳定 ID、名称、状态和类型或路径，让用户选择。不要凭历史记忆或顺序代选。
3. 搜索无结果时说明已经使用的名称，再请用户补充名称或路径；搜索报错时说明错误并排障。只有请求和上下文都没有可用名称、路径或 ID，才在搜索前索要主体信息。

**检查点：** “拿到候选后请用户选择”是必要消歧；“已有名称却不搜索，先索要名称或 ID”是执行遗漏。账期、结算类型等已经确认的口径应保留，不必让用户重新确认。

## 定位顺序

1. 用 `bytedcli babi bill ... --help` 确认当前 flags、枚举和必填项。
2. 加全局 `--dry-run` 检查 method、target、headers 和 body。
3. 仍不清楚时加 `--debug`，并保留 `logId` / `RequestId`。
4. 区分本地参数校验、认证/权限、路由/header、后端业务错误和正常空数据。

| 现象 | 常见原因 | 处理 |
|---|---|---|
| `missing required flags` | 显式参数不完整 | 按 help 补齐；旧脚本才使用完整 JSON `--data` |
| `--data must be a JSON object` | 数组、字符串或无效 JSON | 改为完整 JSON object，不要放 JWT/header |
| 账单日期失败 | Bill 使用毫秒时间戳 | 确保开始不晚于结束 |
| cost 的 `customer_l1...l6_account_id` 被本地拒绝 | 当前 CLI 尚未暴露逐步上线的消费方成本维度 | 记录 CLI 版本；不要改用 `provider_*` 冒充消费主体 |
| `10201006` / `invalid group_key value` | 目标后端尚未部署该分组维度 | 保留 LogID 并报告能力未上线；需要继续时经用户接受后拆成单主体查询并在客户端合并 |
| `product_id` 分组不支持 | 当前主体口径不支持该维度 | 只说明当前口径，不要泛化为接口整体不支持 |
| 成功但 `data.items` 为空 | ID、时间、区域、结算口径、权限或分页不匹配 | 复核 dry-run 后报告空数据与 RequestId |
| `cost_driver_value` 缺失 | 未按 `cost_driver_type` 分组或后端无 CD 数据 | 补充分组并复查；缺失不能当 0 |
| 金额疑似重复 | CD/多维行重复携带金额 | 按账期和业务分组键去重后汇总 |

空结果回复要包含查询对象、时间、区域、分组、分页和 RequestId。不要把后端空数据、命令展示遗漏、认证失败和请求未发送混成一个结论。
