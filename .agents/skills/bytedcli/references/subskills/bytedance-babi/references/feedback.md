# 问题反馈

先区分用户意图：一般问题反馈使用 `bytedcli babi feedback`；用户明确要求 Oncall 时，直接进入下文的 Oncall Skill 流程。
Oncall 不调用反馈命令，也不要双投递。

## 使用中主动建议反馈

无需等用户说“反馈”。结合当前任务的执行结果判断，问题尚未解决时可主动提示并准备草稿：

| 情况 | 处理方式 |
| --- | --- |
| 后端接口报错、服务不可用或超时，阻断任务 | 说明已观察到的错误和已有恢复路径，同时提供反馈选项；不必为了触发反馈再重复请求。 |
| 没有权限或认证失败，任务无法继续 | 优先说明返回的权限申请或登录指引，也可登记“使用受阻”的反馈；反馈不代替授权或登录，不把权限拒绝直接认定为 CLI 缺陷。 |
| 部分字段或金额因权限脱敏，导致用户要求的完整统计无法确认 | 说明已查到的范围、可见金额及缺失范围，不能把可见合计当完整总额；提供包含实际命令、结果限制与完整统计预期的反馈草稿，不把脱敏直接认定为故障，不尝试绕过权限。 |
| 用户指出多次查询不符合预期，或合理排查后结果仍异常 | 核对主体、参数、账期、分页与统计口径，整理已尝试的排查、实际结果及用户预期，再建议反馈；不要无目的地反复查询。 |

可直接修正的参数错误、已经恢复的请求、正常空结果或零金额，不单凭这些现象建议故障反馈。
先按对应领域规则完成排障；反馈选项不替代能继续完成的原任务，也不替用户断言根因。
同一问题在本次对话中只主动建议登记一次；用户拒绝或已登记后，不因后续重试再次建议登记或提交。

出现上述尚未解决且影响任务完成的问题时，在同一次回复中：

1. 说明任务已完成、部分完成或受阻，以及具体证据与限制。
2. 展示包含实际命令、实际结果和用户预期的简短反馈草稿；按下文分开整理问题描述和上下文摘要。
3. 询问“是否提交这条反馈？”。
4. 用户确认后才提交；已经明确授权的具体反馈直接提交一次，不重复确认。

不要只承诺之后再起草，避免让用户先同意起草、再同意提交。复用对话中已有证据，不让用户重填。
草稿中必须写明以下信息（未取得的项省略，不编造）：

- 命令：实际执行的命令路径，例如 `bytedcli babi account list`，以及必要的非敏感参数；不能只写“查询账号”。
- 问题：错误码与错误摘要，或实际结果与用户预期的差异。
- 追踪：实际取得的业务 `logId` / `RequestId`；与反馈提交后返回的日志 ID 区分。

按需补充用户目标与已尝试的排查。版本与可用的用户身份由 CLI 自动附带。
不复制原始请求/响应、完整 debug 日志、环境变量、JWT、AK/SK 或无关业务数据。

正文展示后等待用户同意；用户只是报错或表达不满，不等于授权发送。
用户明确同意该草稿后，按下文直接提交一次，无需再次询问，也无需额外确认参数。
已有明确的反馈正文和提交授权时直接复用，不重复起草或确认。

## 提交问题反馈

先通过 `bytedcli babi feedback --help` 查看当前参数。Agent 预览或提交反馈时，分别整理两个字段：

- `question`（`--message`）：用户要反馈的问题。保留用户表达的含义；用户给出明确正文时保留原文，
  不把整段对话或 Agent 的分析混入问题。
- `summary`（`--summary`）：基于当前对话集中整理与该问题相关的上下文，按“用户输入 → 执行过程与
  实际返回 → Agent 给用户的输出 → 用户后续纠正/预期及未解决项”组织。包含实际执行的命令、
  必要的非敏感参数和已取得的业务 LogID；区分用户陈述、工具返回与 Agent 判断，不把推测写成事实。
  不能只重复 question，也不能只写“查询失败”而遗漏已有的输入、返回或最终回复。

复用已有上下文，不让用户重填。没有历史调用或回复时，摘要只整理已知的输入和预期，并说明
尚无实际调用/输出证据；不为了补摘要执行额外查询，不编造。用户明确不允许附带上下文时省略
`--summary`。两段文本各不超过 8000 UTF-8 bytes；超长时压缩摘要并保留关键事实，不静默截断问题。
摘要使用必要的转述，不复制原始请求/响应、完整对话、debug 日志、环境变量、JWT、凭证或
不相关业务数据。准备草稿时在回复中分别展示“问题描述”和“上下文摘要”，提交授权规则仍沿用上文；
已有明确正文和提交授权时，直接整理摘要并提交，不增加一轮确认。

CLI 自动附带版本、来源等公共属性，
提交和预览（`--dry-run`）都需要有效的当前站点登录身份。认证失败时停止并提示用户按 CLI 指引登录，
不绕过认证或匿名发送，不自动发起登录；实际提交仅附带允许的 JWT 用户属性。

```bash
bytedcli babi feedback --message '问题描述' --summary '相关用户输入、执行结果及 Agent 回复的摘要' --dry-run --format json
bytedcli babi feedback --message '问题描述' --summary '相关用户输入、执行结果及 Agent 回复的摘要' --format json
```

仅预览、起草或讨论时只执行第一条。用户已明确要求提交具体反馈时执行第二条，直接提交，
无需额外确认参数或重复询问；正文或提交意图不清楚时先澄清。

`status=preview` 仅表示预览，回复展示问题正文和已提供的上下文摘要并说明“预览、未发送”。
`status=sent` 与 `trace_id` 表示反馈已提交；返回的 `log_id` 若存在是此次反馈请求的
日志 ID，不能当作被反馈业务命令的日志 ID。不能由提交成功声称问题已处理或已解决。
面向用户只描述反馈内容、状态和必要的追踪信息，不强调底层平台、事件名或存储字段。
失败或结果不明时说明现状，不自动重发，不承诺重试去重。

## Oncall：直接使用 bytedcli 子 Skill

用户明确要求发起 Oncall、提单或建 Oncall 群时，由 Agent 直接加载下述依赖，
从当前对话整理问题描述和已取得的非敏感证据，再按子 Skill 继续。
不要调用 `bytedcli babi feedback` 获取接续信息、预览或创建 Oncall，也不要求用户提供入口 URL。

用户只要起草、预览或讨论时，直接在回复中展示问题草稿和固定租户；已有其他参数则一并展示，
未确定的参数留待正式流程选择。不调用反馈命令、不加载创建流程、不创建追踪工单或群聊，
并明确说明尚未提交。无需为了生成草稿先获得工单 ID。

### 依赖和执行边界

1. 依赖公共 Skill `bytedcli` 和子 Skill **`bytedance-oncall`**。优先读取已安装的 Skill；
   未加载时获取内容：

   ```bash
   bytedcli self skill get bytedcli
   bytedcli self skill get bytedance-oncall
   ```

   必须使用完整名称，`oncall` 可能匹配多个 Skill。读取公共 Skill 后按其规则确认命令面；
   完整读取 Oncall 子 Skill 的 `references/escalation.md`，再按阶段加载其引用文件。
   文件不在本地时使用 `bytedcli self skill get bytedance-oncall/references/escalation.md` 等完整路径获取。
   bytedcli 未安装时，按[安装指引](babi-troubleshooting.md#oncall-缺少-bytedcli)提供安装方法，安装成功后再加载上述 Skill。
   依赖 Skill 无法读取或认证不可用时，说明实际缺失项和该依赖的修复指引，
   停在依赖处；不要改用其他 Oncall 产品、手写 HTTP、打开旧 URL 或回退提交一般问题反馈。
2. BABI 入口的租户固定为 **786（BABI）**。把它作为已确定的租户交给子 Skill，跳过租户搜索；
   租户详情、问题分类、追踪工单和最终建群均使用 786。用户指定其他租户时说明本入口限制并停止，
   不能提供租户覆盖参数；服务端分类要求 `switch_tenant` 时展示实际目标和原因并停止，不能跨租户创建。
3. 问题描述、优先级、区域和分类由用户与 Agent 根据上下文、当前命令帮助和租户实际返回项选择；
   不在 BABI 中固定这些值，不编造分类 ID，不把运行站点当作问题区域。缺少必要信息时按子 Skill 补齐。
4. 具体排查、停止条件、P0 事故影响要求和最终建群确认全部遵循 Oncall 子 Skill，不在本文件另建流程。
   工单 ID 取自当前流程本次 `flow create` 的实际返回，无需用户事先提供。
   `flow create` 成功只表示创建了追踪工单；只有 `chat create` 实际成功才能说“已发起 Oncall”。
   失败或结果不明时据实说明，不自动重复创建。
