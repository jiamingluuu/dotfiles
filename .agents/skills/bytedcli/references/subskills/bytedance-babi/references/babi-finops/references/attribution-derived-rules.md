# 归因派生规则

本文件定义如何把 Insight、账单、监控和负责人证据收敛为 `babi_finops_attribution_v1`。这些规则决定业务主因和责任主体；CLI renderer 只负责按固定模板输出，不替调用方补造证据。

## 输入证据

只使用实际返回并可追溯的证据：

- 实例详情：主体、报告期、基准期、状态和统计口径。
- 分大区总览：当期、基准期、波动金额和幅度。
- 异常贡献：用量、单价、本期新增、本期缺失、摊销代持等原因及贡献金额。
- 归因树：`id/name/full_name/value/main_contributor/contributors/children`。
- 监控：对象、监控项、账期、报警 ID、报警链接和能解释的金额。
- Product/ByteTree/负责人：正式名称、稳定 ID、完整路径、计费方式、产品线和实际负责人。

归因工单只提供本次写回所需的 `ticket_id`、Insight 关联和 Oncall 链接。历史工单中的
`attribution_conclusion`、`attribution_conclusion_html`、`final_conclusion` 和
`related_owners` 不属于可追溯的当前 Insight 证据，禁止复制到 `report.json`、用于主因派生
或作为最终回复。工单关联复用与归因内容复用是两个独立概念。

不同接口金额不闭合时不得相加。优先在同一条归因路径中比较，保留 `attribution_path_records`、剪枝参数、`truncated/errors` 和 `logId`。

## 同向与反向

1. 先根据总波动确定主方向：上涨只把正贡献作为同向，下降只把负贡献作为同向。
2. 同向贡献用于判定主因，按 `abs(fluctuated_value)` 排序取 Top5。
3. 反向贡献单独取 Top5，只用于解释净额抵消和完整性，不覆盖同向主因。
4. “本期新增”与“本期缺失”同时存在时分别保留，禁止只写净额后声称单一原因。
5. 每个事件、同向项和反向项都保留当期金额、基准期金额、波动金额与幅度；接口未返回时明确写“未返回”。

## 共同对象收敛

把原始路径归一为：

```text
area -> root_service_tree -> service_tree/psm -> cost_product -> charge_item -> factor
```

按以下顺序派生主链路：

1. 找共同大区：同向主要金额集中在同一大区时从该大区开始；没有大区证据时从分析对象开始。
2. 找共同服务树：多个商品或多个叶子同落在一个可治理父服务树下时，上卷到共同父节点，不把最大叶子写成整体主因。
3. 找共同计费项：同时执行 `cost_product -> bytetree -> charge_item` 和 `cost_product -> charge_item -> bytetree`。多个高贡献业务域共同收敛到同一“计费单元 + 售卖区域”时，计费项可进入主链路。
4. 找主因因子：优先使用异常贡献或节点全部 `contributors` 中的同向主因，例如用量、单价、摊销代持源成本、本期缺失。
5. 确定 `action_object`：选择能代表主要同向金额且可治理的共同业务对象；成本商品是受影响对象时，不能默认它就是责任对象。

计费项必须按“计费单元 + 售卖区域”展示。只有 flavor 没有 region 时写“计费单元”，不得伪装成完整计费项。

互补路径都未返回下一层时写“下钻未返回”，禁止补造服务树、PSM 或计费项。

## 覆盖率门禁

深层服务树、PSM、叶子或计费项进入主链路前必须计算：

```text
leaf_coverage = abs(sum(同一候选链路的同向叶子金额)) / abs(上层对象或事件波动金额)
```

计算要求：

- 分母使用闭环行对应商品的波动金额；全局主事件才使用事件总波动。
- 分子只包含同一候选链路的同向叶子，不混入反向项、其他商品、其他大区或其他接口口径。
- 多个叶子共同构成同一链路时可以合并，但证据里逐个保留金额。

门禁：

| 覆盖率 | 结论 |
|---|---|
| `<20%` | 只能作为局部证据，禁止进入主链路和 `action_object` |
| `20%-<50%` | 默认不是主因；只能在其余金额属于同一业务动作时上卷到共同父节点 |
| `50%-<80%` | 可作为候选主因；兄弟节点分散时仍需上卷 |
| `>=80%` | 可称为解释绝大多数波动，但仍保留兄弟节点复核结果 |

覆盖率是派生证据，不写入最终“归因链路”或“建议动作”文案；低覆盖率 raw 路径放在证据区。

## 数据质量门禁

出现本期全部缺失、NaN、推量失败、推量延迟、计量失败或出账不完整时：

1. 按 Insight 返回的商品 ID 查询本期和基准期监控。
2. 只有报警对象、账期、计费项和金额能够对应时，才把该金额归到商品方计量问题。
3. 某个商品命中报警不能泛化成其他商品或整棵服务树的主因。
4. 监控已解释对应缺失金额时，主链路停止在商品/监控项/可治理父服务树；更深孙节点只作为 raw 证据。
5. 未命中时写“未发现商品计量/出账监控异常信号”，继续复核真实使用和账期；不得写“监控正常，所以业务正常”。
6. 建议动作必须包含明确结论，如未推量、推量失败、推量延迟、计量失败或出账未完整，以及对象、账期、报警 ID/链接和可解释金额。

## 单位 CD 成本

只对 `data_range_type=1` 的 BABI 账号执行：

1. 总体事件和每个波动成本商品分别形成 `unit_cd_cost_assessments[]`。
2. 每个匹配指标独立一项，展示指标名、CD 波动幅度、成本波动幅度、单位 CD 成本波动幅度、正常/异常和驱动判断。
3. 不得在最终 Markdown、HTML、飞书文档或 JSON 中出现 CD 基准/当期原值、`cd_base`、`cd_current` 或绝对单位 CD 成本。
4. 只有账号级 CD 时，逐商品写“未返回商品粒度 CD 或单位成本”，不得复用总体判断。
5. 非 BABI 账号写“不适用（非 BABI 账号）”。证据不可用时写明确原因。

## 责任主体与负责人

| 证据 | 责任主体 | `action_object` | 动作 |
|---|---|---|---|
| 用量变化，未命中计量报警 | 业务方主责 / 商品方协同 | 共同服务树、PSM 或业务对象 | 业务方确认任务、活动、流量、下线、扩缩容或调度；商品方协同核对计费口径 |
| 用量变化且命中推量/计量报警 | 商品方主责 | 命中商品或计量对象 | 补推、重算、修复计量或账期回补 |
| 本期缺失/NaN 且监控命中 | 商品方主责 | 命中商品或计量对象 | 处理推量或出账完整性，并限定可解释金额 |
| 本期缺失/NaN 且监控未命中 | 待复核 / 业务方协同 | 缺失贡献对象 | 继续复核真实使用、账期和接口返回 |
| 摊销代持源成本变化 | 商品方主责 / 业务方协同 | 商品或归属服务树 | 商品方确认摊销/归属规则，业务方确认真实使用 |

负责人必须来自 `action_object` 或监控命中的商品/计量对象：

- 商品计量问题使用商品/计量负责人。
- 业务变化使用实际命中的服务树/PSM 负责人；多节点共同解释时合并去重。
- 查询不到时写“负责人未返回”，不得写猜测的人名或“xxx owner”。
- 优化建议只是治理补充，不改变已由归因证据确定的责任主体。

## 事件级 Why

每个正式归因事件必须独立生成 `root_causes[]`：

```text
原因结论（已有） -> 具体事件（+链接） -> 影响范围 Top5（如有）
```

规则：

1. `cause` 使用已证实原因；未闭合则状态写 pending/unconfirmed，不把推断写成事实。
2. `event_url` 使用实际事件/洞察链接；没有时固定输出“未绑定，证据为当前洞察实例”。
3. `impact_scope_top5` 只放属于该原因、同口径、同单位的 Top5，不复用其他事件或全局 Top5。
4. 没有可分摊 Top5 时固定输出“暂无可分摊 Top5”。
5. `amount/share_text/action/owner_role` 必须与同一事件证据一致。

## 生成前校验

回填前逐项检查：

1. 主方向与同向/反向集合是否正确。
2. 主链路是否为派生后的共同对象，而不是未经归纳的最深 raw path。
3. 深层叶子进入主链路前是否计算覆盖率并通过门禁。
4. 多服务树共同计费项是否经过两条互补路径交叉验证。
5. 数据质量告警是否只解释自己的商品和金额。
6. 责任主体是否明确，负责人是否来自 `action_object`。
7. BABI 账号总体和逐商品单位 CD 成本判断是否齐全且无原值泄露。
8. 每个事件是否有独立 `root_causes[]` 和本事件 `impact_scope_top5`。
9. `truncated/errors`、剪枝和未返回层级是否在证据中保留。
10. `attribution_path_records` 是否只包含实际执行链路。
11. `report.json` 是否只放本次即席查询得到的结构化事实，且没有历史工单结论、历史负责人或模型自由撰写的最终结论字段。
12. `final-reply.md`、工单 `conclusion.md` 和 HTML 是否来自同一次 renderer 输出，`input_sha256` 是否一致，并分别核对 `reply_sha256` / `conclusion_sha256`。
