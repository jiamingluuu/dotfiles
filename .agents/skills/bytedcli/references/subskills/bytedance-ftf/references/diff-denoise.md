# FTF Diff 降噪分析

## 用途

当用户要求分析 FTF task / flow diff 时，在进入根因归类或代码关联前，先用本文件做降噪检查。降噪检查是必经步骤，但不要求强行给出降噪结论；证据不足时直接说明“未发现可剔除降噪项”或“样本不足，暂不降噪”。

> 本文件既是独立 L1 降噪知识库，也是编排流程中归类前的**强制前置工序**
> （见 `diff-analysis.md` 标准流程第 5 步）。

本文件只指导 Agent 基于任务结果可见证据做只读分析。不要调用外部智能归因服务，不读取 TCC，不写回 FTF 归因，不把组件支持、FTF 产物启动、context 透传等任务结果外前提写成已确认事实。

## 输入证据

只使用当前 task / flow 查询结果、用户提供的明细或日志证据：

- method、direction、内部 diff 标识、logId。
- diff path、base path、replay path、累计 diff 明细条数、命中流量数、影响样本范围。
- 多条独立流量中的 base value / replay value 样本。
- 数组元素明细、元素字段、元素数量、排序前后的匹配情况。
- 字段所属业务上下文，例如订单、商品、售后单、履约、金额、状态、配置、trace 等。

样本覆盖的独立 logId / flow 越多，结论置信度越高。不要写死“多少条才算大量”；样本量只作为置信度参考。

## 随机值 Diff

优先使用 `ftf diff path-profile get` 获取跨流量分布证据：

```bash
bytedcli --json ftf diff path-profile get \
  --url "<ftf-task-url>" \
  --psm example.psm \
  --method GetDemo \
  --diff-path "Ret->dynamic_id" \
  --sample-size 20
```

命令输出里的 `randomLikeSignal` 只是置信度参考。Agent 必须结合字段语义输出判断依据，不能只凭 confidence 定性。

随机值排除必须同时具备两类证据：

1. 跨流量分散证据：同一 path 在多条独立流量里出现 diff，且不同流量的 base value 和 replay value 都没有稳定聚类。
2. 字段语义证据：path、字段名或上下文语义支持它是动态值、随机值或请求外生成值。

常见候选包括：

- trace、span、request、log、nonce、token、signature、uuid、随机实验桶、动态文案、时间戳、过期时间、临时 key。
- `request_id`、`log_id`、`schema_log_id`、`sign_token`、`x-signature` 这类追踪 ID / 签名 token / URL 签名字段，字段语义本身就是强证据；结合样本分散、平台既有标注或多流量 profile 时，可以作为高置信噪音输出。
- 每次执行都会生成的新标识，且该标识不作为业务对象主键参与后续状态判断。

反例要保守处理：

- 金额、数量、状态、权限、库存、配置开关、排序权重、结算结果、风控结论、业务对象 ID 等字段，即使值分散，也不能直接按随机值排除。
- 如果值集中在少数枚举、固定区间或稳定业务状态上，应降低随机值置信度，并进入根因分析。
- 只有单条或少量样本时，只能标为随机值候选，不能从主根因链路剔除。

输出时说明：

- 涉及 path 和样本范围。
- base/replay value 是否都无稳定聚类。
- 字段语义为什么支持随机性。
- 降噪处理级别和处理方式：可剔除项从主根因链路移除、待核验候选降低权重、证据不足项不降噪。

## 数组乱序 Diff

优先使用 `ftf diff array-check get` 获取两侧数组明细和排序比较结果：

```bash
bytedcli --json ftf diff array-check get \
  --url "<ftf-task-url>" \
  --similar-diff-id sample-similar-diff \
  --key sample_id \
  --sample-size 5
```

如果没有显式 `--key`，命令会基于数组元素字段推断候选主键；Agent 必须输出主键推断依据，并确认该 key 在业务语义上代表同一个对象。

数组乱序排除必须基于两侧流量明细，而不是只看 diff path。Agent 可以推断排序主键，但必须输出推断依据。

判断步骤：

1. 确认 diff 来自数组元素顺序差异，先比较两侧数组长度和元素集合。
2. 从元素字段里推断业务主键或稳定排序键，例如 id、item_id、sku_id、order_id、after_sale_id、relation_id 等。
3. 说明主键选择依据：字段在数组元素内是否唯一、是否稳定、是否代表同一个业务对象。
4. 按该主键对 base/replay 两侧数组排序后，再比较完整元素。
5. 判断数组顺序是否有业务语义。若顺序代表优先级、展示顺序、匹配顺序、命中顺序或结算顺序，不要按乱序排除。

结论分三类：

- 纯数组乱序：按主键排序后两侧数组完全一致，可作为可剔除降噪项。
- 数组乱序 + 随机值：按主键排序后业务对象能一一对齐，剩余 diff 只落在随机值字段上，可作为待核验降噪候选；输出要拆开“主键对齐证据”和“随机值证据”。
- 数组元素可对齐但仍有字段差异：FTF 可能把同一数组 path 拆成 base-only / replay-only 两类 diff 聚类。此时先用业务键对齐元素，再说明剩余字段差异；不要写成纯数组乱序。
- 不能降噪：主键重复、缺失、冲突，排序后仍有业务字段差异，或数组顺序本身有业务语义。

输出时说明：

- 使用的排序主键。
- 主键唯一性、稳定性和业务对象含义。
- 排序前 diff 表现和排序后匹配结论。
- 是否还有剩余业务字段差异。
- 顺序是否有业务语义，以及为什么。

### 成对元素聚类表达模板

当同一条流量、同一个数组 path 同时出现“录制侧有对象/回放侧为空”和“录制侧为空/回放侧有对象”两类 diff 聚类时，不要直接输出“两个镜像 cluster”、不要用 `similarDiffId` 当主语，也不要只写 `diffCount/logCount`。优先按下面口径写：

```text
这条流量的 <array_name> 数组里有 <N> 个业务对象。FTF 没有把录制侧和回放侧的数组元素直接对齐起来，因此表现为两类 diff 聚类：一类像“录制侧多了 <N> 个对象”，另一类像“回放侧多了 <N> 个对象”。按 <key_a> + <key_b> 对齐后，<M> 个对象都能匹配；对齐后仍存在 <remaining_path> 等字段差异，需要业务确认这些剩余字段差异是否可忽略。
```

如果需要说明规模，用“命中流量数”和“累计 diff 明细条数”：

```text
该 path 覆盖 <log_count> 条流量，累计记录 <diff_count> 条 diff 明细。明细条数会受数组元素数量影响，只用于说明规模，不代表 <diff_count> 个独立问题。
```

写这段时要同时输出推断依据：

- 为什么选择该业务键：字段是否在元素内唯一、是否稳定、是否代表同一个业务对象。
- 对齐结果：两侧元素数量、能匹配多少个对象、是否存在未匹配对象。
- 剩余差异：对象对齐后仍不同的字段 path，不要把“能对齐”写成“完全一致”。
- 结论边界：这类情况最多说明“数组元素身份可对齐”，不能自动说明“纯数组乱序可忽略”。
- 可复核入口：如果有 diff / flow 直达链接，附在结论后；没有链接时给出 task URL、method、path 和代表 log_id，不要编造链接。

## 降噪判定与剔除

- 可剔除降噪项：证据充分的随机值 diff，或数组按稳定业务主键排序后完全匹配。可从主根因链路剔除，但报告中保留证据。
- 待核验降噪候选：样本覆盖不足、字段语义支持但分散证据不充分，或数组排序后只剩随机值类差异。不要剔除，只降低权重，继续参与根因分析。
- 证据不足降噪项：没有足够样本、没有明细、没有可解释主键，或顺序语义不明确。不降噪，不剔除，只说明缺少哪些证据。

以上是降噪处理状态，不是 Finding 的 `confidence`。生成 Finding 时，`confidence` 仍然只能填写“高 / 低”，不得把“待核验”等降噪状态写入该字段。

## 输出结构

在 diff 分析报告中固定增加：

```text
降噪判断
- 可剔除降噪项：
- 待核验降噪候选：
- 不应降噪：
- 证据不足/待补充：
```

每条随机值判断至少写：

- diff path、样本范围、base/replay 分布特征、字段语义、置信度、处理方式。

每条数组乱序判断至少写：

- 排序主键、主键选择依据、排序后匹配结论、顺序是否有业务语义、置信度、处理方式。

## 不要推断

- 不要把“值不一样”直接等同于随机值。
- 不要把“数组 path 看起来互换”直接等同于数组乱序。
- 不要在缺少流量明细时声称排序后完全匹配。
- 不要因为某个字段名像 `id` 就默认它是排序主键；需要唯一性、稳定性和业务语义支撑。
- 不要把外部配置、历史频次、录制链路状态或智能归因结果当成当前任务已证明事实，除非用户明确提供了对应证据。
