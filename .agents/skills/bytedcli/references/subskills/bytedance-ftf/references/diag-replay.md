# FTF 回放无流量诊断（编排层）

## 适用范围

当用户反馈“回放没有流量”“回放任务无数据”“任务没有拿到流量”或任务因无流量结束时，
用本文件判断流量模式，并沿来源、筛选、消费和下游执行链路定位断点。用户反馈“录制不到
流量”“采集不到流量”且没有回放任务语境时不进入本文件，直接读取 `diag-record.md`。

参考资料：

- 《FTF2.0 ByteCopy 无流量排查手册》（内部文档；脱敏锚点：ByteCopy 无流量）
- 《FTF2.0 流量回放 One Page》（内部知识库；脱敏锚点：回放无流量）

这两份文档是排查线索，不是高于运行事实的结论。当前 CLI 帮助、源码、Schema、任务/Flow
响应、日志和请求响应证据与其冲突时，以直接证据为准，并在结论中说明冲突。文档中的
ByteCopy/SDK 采集排查只适用于实时流量链路。

## 输入门禁

回放无流量诊断至少需要 **任务 ID 或任务链接**。PSM、环境、Method、PID/LogID 和发生时间
可提高定位效率，但不能替代任务定位信息。缺少任务 ID/链接时先索取，不用 PSM 猜任务，也
不先转成独立的录制问题。

## 1. 固定任务身份并判断流量模式

任务链接先本地解析，再查询任务；不要手工拆链接：

```bash
bytedcli --json ftf target parse --url "<ftf-url>"
bytedcli --json --site cn ftf task get --id <task-id> \
  | jq '.data | {id, status, detail_status, case_filter_mode, run_psm, env, task_flow_count, case_count, fail_case_count, update_time}'
```

示例第二行是 cn 路由。URL 命令自身会自动派生站点；工作流仍须将解析结果与用户明确声明的
目标站点对比，如不一致，在任何派生 ID 查询前停止。解析结果为 zg 时必须使用
`bytedcli --json --site cn --vregion China-Pay ftf ...`；后续所有从 URL 派生 ID 的命令都冻结
并显式复用该路由。若输入只有裸 ID，先要求明确 cn/zg，不得猜站点。

以任务响应中的 `case_filter_mode` 为准，枚举见 `enums.md#case_filter_mode`：

- `0`（实时流量）：先排查实时采集，再继续排查消费与下游回放链路。
- `1/2/3/4/6/7`（场景、历史、手动圈选、第三方、智选、自定义）：不要套用 ByteCopy/SDK
  实时采集手册；从来源数据是否存在、任务时间窗、Method/高级筛选、用例集和来源注入结果
  开始核对。
- 字段缺失或出现未知值：不能默认实时；输出证据缺口，先通过当前 Schema、CLI 输出或平台
  oncall 确认模式。

`status=7`、`task_flow_count=0` 或连续无流量提前结束只说明“任务没有拿到可回放流量”，不
是根因。实时任务还要在任务或关联计划快照可见时核对 `noflow_abort_duration`；该字段未
回显时只记为证据缺口，不能把 `null` 当成未配置。低 QPS、短运行时长或较短无流量终止阈值
可能让任务在下一条样本到达前结束，但仍需用时间线证据确认。

## 2. 非实时流量：从来源库存和筛选漏斗定位

按“来源有数据 → 时间窗命中 → PSM/Method/高级筛选命中 → 任务接收用例”建立漏斗。优先
读取任务的 `psm_replay_param_detail`、`advanced_filter_group_brief/list`、`case_count` 和
`task_flow_count`；必要时读取对应计划配置并与任务快照对照。

将首个从非零变为零的层级作为失败断点。若当前 CLI/API 不暴露来源库存或筛选命中数，只能
把该层标为“待平台侧核实”，不能改查实时采集日志，也不能把“筛选后为零”猜成“来源无数据”。

## 3. 实时流量：从采集到下游回放链路

实时任务委派 `diag-record.md` 时跳过它的首次症状分诊，直接用任务中的 PSM、环境、Method 和
时间窗核对对应采集分支，再继续
检查下游回放链路；采集正常不是本诊断的停止点。若任务中已有样本，可读取单条 Flow 的来源
辅助确认实际采集源；完全没有 Flow 时 `flow_source` 不存在，不能据此猜测 ByteCopy 或 SDK：

```bash
bytedcli --json --site cn ftf task flow get --task-id <task-id> --pid <pid> \
  | jq '.data.diff | {flow_source, psm, method, log_id, replay_status_code, failed_reason}'
```

无论 ByteCopy/SDK 采集是否正常，都要按下表确定“最远通过点”和“首个失败点”，直到业务
服务收到回放请求并返回响应，或明确记录无法继续取证的边界：

| 链路段                     | 通过证据示例                                                                            | 未通过时的定位方向                                |
| -------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 上游真实请求               | 业务 QPS、目标实例访问日志或已知 LogID 落在采集窗                                       | 环境/泳道、Cluster、IDC、路由、时间窗或本来无请求 |
| ByteCopy 采集              | ByteCopy 收包证据                                                                      | 按 ByteCopy 故障树核对采集配置、采样和收包        |
| ByteCopy 消费与保存        | `bytecopy_flow_parse_ok`、`flow_bytecopy_rate_limit`、格式检查、保存证据时间线一致       | ByteCopy 消费、解析、限流、格式转换或保存失败      |
| SDK 插桩与发送             | SDK 初始化、插桩和 `[FTF-INFO] send inbound req message success` 的同窗证据              | 按 SDK 故障树核对产物、插桩、配置和发送链路        |
| Executor 消费并通过限流    | `ftf.nova.executor.nova_executor_realtime_after_limit` 有对应样本                       | Executor 消费积压、任务过滤或执行侧限流           |
| Replayer 发起请求          | `ftf.nova.replayer.consume_time_flow_replay_cost_time` 或同任务/LogID 回放日志          | Replayer 调度、序列化、连接、鉴权或发送失败       |
| 目标业务收到并响应         | 目标 PSM 访问日志、回放 LogID、响应状态/错误                                            | 服务发现、路由、环境、网络、业务处理或响应异常    |

指标名只用于检索同一任务/PSM/时间窗的证据，单个指标“存在”不等于该任务已通过该节点。
ByteCopy 与 SDK 证据链必须分开；SDK 分支不得复用 ByteCopy 专属指标证明采集或消费成功。
优先关联任务 ID、PSM、Method、PID/LogID 和时间戳；日志或监控需要通过获准的观测能力查询。
CLI 取不到时，输出具体的待核实指标/日志和维度，不得伪造查询结果。

若已经产生 Flow 但 `data.diff.failed_reason != 0`，进入 `diag-replay-failure.md`，用错误码做
预分类并继续核对日志、请求/响应、配置和代码。未知兜底错误码不能作为最终根因。

## 结论规则

1. 用连续证据确定最远通过点，再把紧邻的第一个失败节点作为首要定位范围；不要从末端现象
   反推上游组件一定有问题。
2. “未发现日志”“计数为零”和“CLI 无字段”分别表示未观察到、观察为零和证据不可见，三者
   不能混为同一结论。
3. 直接代码、日志、任务响应或请求/响应推翻手册预定义解释时，采用直接证据并注明手册仅作
   初始排查方向。
4. 无法闭环时输出“根因未定位”，列出已排除节点、首个证据缺口和唯一下一步；不要以未知、
   无流量状态或笼统的平台问题结案。

## 输出

按 `replay-diagnosis.md#报告口径` 输出，并额外包含：

- 问题类型、任务 ID/链接是否齐全、任务流量模式；
- 实时任务的采集侧核对结果，以及非实时任务的来源库存和筛选漏斗；
- 链路最远通过点、首个失败点及对应时间线证据；
- 已确认根因、待验证项和证据冲突；
- 一个最小下一步，写明查询对象、时间窗和验证成功标准。
