# NSG 规则模型与来源

本 reference 用于解释 NSG 规则本身：字段、合法性、来源、扩展、域名匹配、ID、优先级及已知限制。它不改变命令路由：普通跨来源查询仍使用 `nac rule search`，明确查询编译后或已下发数据面的规则集合才使用 `nac admin compiled-rule list`；查询某条规则的下发情况或下发阶段使用 `nac admin rule delivery-status --id <rule-id>`。

这里的“来源”是 NSG 正式规则在规范化或编译结果中的来源分类，不等同于 bytedcli 的命令资源名。四种来源只描述正式规则，不包含独立表中的 Gray Rule。尤其是：

- Honeycomb 来源对应当前 MGT Rule 的 NSG 部分。
- Yunque/MySQL 来源对应 Yunque Rule（管理员规则）的历史存储与编译来源。
- NAC Security Center 来源在返回值中也可能写作 `nac_sec`；历史代码中的 `NUC` 是 `NAC` 的拼写遗留，指同一来源。
- TCC 来源只用于解释 NAC 查询返回的规则来源。直接读取 TCC 配置属于外部平台工作流，不由本 Skill 执行。

## 字段与可配置性

| 字段 | 含义 | 用户可配置 | 约束或转换 |
|---|---|---:|---|
| `L3_PROTO` | 网络层协议 | 否 | 根据源、目的地址推导 IPv4/IPv6；两端均为通配时也为通配 |
| `L4_PROTO` | 传输层协议 | 是 | 表示 TCP、UDP、ICMP 等传输层匹配条件 |
| `SRC_ADDRESS` | 源 IPv4/IPv6 地址 | 是 | 接受单个合法地址或 CIDR |
| `DST_ADDRESS` | 目的 IPv4/IPv6 地址 | 是 | 接受单个合法地址或 CIDR |
| `SRC_PORT` | 源端口 | 是 | 接受单端口或端口范围 |
| `DST_PORT` | 目的端口 | 是 | 接受单端口或端口范围；与目的域名组合时有限制 |
| `SRC_PSM` | 源 PSM | 是 | 管理面转换为 ClusterID，NSG 后端再解析为 IP 列表 |
| `DST_PSM` | 目的 PSM | 否 | 当前规则模型不支持 |
| `SRC_PSMID` | 源 PSM ID | 否 | 从 `SRC_PSM` 转换，不能直接配置 |
| `DST_PSMID` | 目的 PSM ID | 否 | 当前规则模型不支持 |
| `SRC_DOMAIN` | 源域名 | 否 | 当前规则模型不支持 |
| `DST_DOMAIN` | 目的域名 | 是 | 与目的 IP 互斥，并受目的端口规则约束 |

未显式设置的控制面字段在规则匹配中按通配符 `*` 处理。

## 合法规则

按 NSG 的规范规则模型检查时，必须同时满足以下条件：

1. 空字段与 `*` 都表示 wildcard；不能把未设置字段解释为精确空字符串匹配。这里描述的是控制面规则定义；`nac rule search` 的候选五态和已有规则三态见 [rule-search.md](rule-search.md)。
2. 地址必须是合法的单个 IPv4/IPv6 地址或合法 CIDR。
3. 端口必须是 `0` 到 `65535` 的单个数值，或 `lowPort-highPort` 范围；范围下界必须小于上界。
4. 源地址、源域名、源端口、源 PSM/PSMID、目的地址、目的域名、目的端口、目的 PSM 和传输协议不能全部为空。
5. `SRC_ADDRESS` 与 `SRC_PSM` 互斥；两者可以都不配置，此时源身份为通配。
6. `DST_ADDRESS` 与 `DST_DOMAIN` 互斥；两者可以都不配置，此时目的身份为通配。
7. 配置 `DST_DOMAIN` 时，`DST_PORT` 不能使用端口范围。
8. 同一规则不能混用 IPv4 与 IPv6 地址。`L3_PROTO` 从 `SRC_ADDRESS`、`DST_ADDRESS` 推导；两者均为通配时，`L3_PROTO` 也为通配。
9. 令 `SRC_ID = SRC_ADDRESS | SRC_PSMID | *`，`DST_ID = DST_ADDRESS | DST_DOMAIN | *`，规范模型要求两者不能同时为 `*`。

最后一条在不同历史来源中的实际执行并不一致，尤其要结合“已知限制”判断控制面规则是否真的进入编译结果。

## 正式规则来源

NSG 的正式规则结果可能同时包含四个历史来源：

| 来源 | 当前含义 | 编译链路特征 |
|---|---|---|
| TCC | 历史配置面规则 | 与 NAC Security Center 规则同时被 XACL 与 NSG 使用；ID、优先级和反向规则按来源算法生成 |
| NAC Security Center | 旧、新两代安全中心规则 | 旧规则已冻结；新规则仍可能经接口写入；返回来源常见为 `nac_sec` |
| Yunque / MySQL | Yunque 管理规则 | 历史上保存在 NAC 管理侧的规则表中，能力逐步迁往 Honeycomb |
| Honeycomb | 当前主要的规则维护入口 | 管理面先完成翻译并把结果透传给 NSG 后端 |

不要根据单一字段猜来源。需要判断时，优先使用返回的来源字段；没有来源字段时再按 ID 区间反查。

## 灰度规则的 Agent 定向叠加

灰度规则保存在独立表中，不属于上述四种正式规则来源。它不进入 `nac rule search` 使用的正式规则数据集，因此规则匹配接口查不到灰度对象。查询边界是：

- `nac rule search`：查询编译前但已 normalize 的四来源正式规则。
- `nac admin gray-rule list`：查询独立表中的灰度规则定义、目标、操作与发布状态。
- `nac admin compiled-rule list`：查询准备下发数据面的最终编译结果；服务端读取正式规则后，根据请求链路的 `X-Real-IP` 动态叠加命中的发布中灰度规则，因此结果可能包含灰度效果。

CLI 的 compiled-rule 命令没有 `--agent-ip`，不能把当前请求结果解释为对任意 Agent 的模拟。需要判断一条灰度规则覆盖哪些 Agent 时，应读取 gray-rule 的目标类型和值：

| `target_type` | 命中含义 |
|---|---|
| `ALL` | 所有 Agent 都命中 |
| `IP` | `target_value` 支持单 IP、CIDR 和 IP 范围；请求 IP 落入任一值即命中 |
| `CLUSTER` | 读取 `nsg_cluster_map`，按目标集群名查成员 IP，只有请求 IP 属于目标集群才命中 |

命中后只修改当前 Agent 的本次规则集合，不直接改变其他 Agent 的结果：

| `op_type` | 对当前 Agent 规则集合的效果 |
|---|---|
| `ADD` | 在当前 Agent 的规则集合中增加灰度翻译后的规则；生效规则使用灰度 ID 空间 |
| `UPDATE` | 删除 `origin_id` 对应的正式规则及其正反向、IPv4/IPv6 形态，再加入灰度版本 |
| `DELETE` | 只从当前 Agent 的结果中删除 `origin_id` 对应的正式规则及其正反向、IPv4/IPv6 形态，不加入替代规则 |

`UPDATE` 有保护逻辑：灰度规则的预翻译结果为空时跳过本次更新，保留 `origin_id` 正式规则，避免因为 DNS/PSM 翻译失败先删除正式规则。`ADD` 缺少预翻译结果时也会跳过注入。

## 两阶段扩展

控制面配置不会原样成为最终数据面规则，而是经过两级扩展。

### Phase One：来源相关扩展

第一阶段按规则来源与规则集补齐或生成规则 ID、优先级和反向规则。原说明中的来源差异可整理为：

| 来源 | ID/优先级处理 | 反向规则处理 |
|---|---|---|
| TCC | 按规则名排序与公式生成 | 只为跨境规则生成 |
| NAC Security Center | 按安全中心 ID、subclass、规则类型推导 | 除特定出向安全组类型外生成 |
| Yunque / MySQL | 保留规则 ID 和用户设置的优先级 | 仅 `reversed=true` 时生成 |
| Honeycomb | 管理面分配 ID 与优先级，NSG 后端透传 | 管理面负责生成，NSG 后端不重复生成 |

无论来源如何，公网出向规则类型 `idc_out.gw` 都不生成反向规则。Honeycomb 的“自动生成反向规则”指管理面行为；从 NSG 后端视角看，这些规则已经完成扩展，因此后端只做透传，两种表述并不冲突。

### Phase Two：字段翻译

第二阶段由 NSG 后端把抽象选择器翻译为数据面可执行字段，主要包括：

- 将 PSM/PSMID 展开为 IP 列表。
- 将目的域名解析或扩展为用于匹配的地址信息。

因此 `nac rule search` 的编译前 normalize 结果与 `nac admin compiled-rule list` 的数据面结果可能一对多，也可能因合法性或来源限制而没有对应编译规则。

## 域名规则匹配

NSG 只支持目的域名匹配，不支持源域名。它会对 HTTP/TLS 流量解析域名后再匹配规则：

| 规则条件 | 标准 HTTP/HTTPS（目的端口 80/443） | 非标准 HTTP/HTTPS 端口 |
|---|---:|---:|
| 只配置 `DST_DOMAIN` | 可匹配 | 不匹配 |
| 同时配置 `DST_DOMAIN` 与单个 `DST_PORT` | 可匹配 | 可匹配 |

查询或解释非标准端口的域名规则时，必须检查规则是否同时声明了对应的单一目的端口。不要仅凭 `DST_DOMAIN` 判断它能覆盖任意端口。

## 规则 ID 与来源反查

基础规则的来源 ID 区间彼此分离，灰度和反向规则则在基础 ID 上增加固定偏移：

| ID 区间或算法 | 来源/形态 | 说明 |
|---|---|---|
| `[3, 约 80,000)` | 旧 NAC Security Center | 已冻结，不再新增 |
| `[100,000, 5,000,000)` | Yunque / MySQL | 当前实际有效数据的下限高于区间理论下限 |
| 从 `5,000,002` 起按偶数递增 | TCC | 基础 ID 等于换算后的优先级加 `5,000,000`，数量取决于该 `rule_type` 的规则数 |
| `[10,000,000, 20,000,000)` | 新 NAC Security Center | 仍可能有新增规则 |
| `[20,000,000, 30,000,000)` | Honeycomb | 由管理面分配并由 NSG 后端透传 |
| `[30,000,000, 100,000,000)` | 灰度注入 | 生效 ID = 基础 ID + `30,000,000` |
| `>= 100,000,000` | 反向规则 | 反向 ID = 原规则 ID + `100,000,000` |

反查来源时顺序固定：

1. ID 不小于 `100,000,000` 时，先减去 `100,000,000`，并标记为反向规则。
2. 还原后的 ID 位于灰度区间时，再减去 `30,000,000`，并标记为灰度注入。
3. 用最终基础 ID 对照来源区间。

必须先去掉反向偏移，再判断灰度偏移；反过来会错误识别“灰度规则的反向规则”。区间只能作为返回缺少来源字段时的辅助判断，不能代替接口明确返回的来源。

## 规则优先级

NSG 规则优先级总体范围是 `[0, 2^29-1]`。优先级数值越小，优先级越高，`0` 为最高优先级；同优先级时再依据具体来源的稳定排序规则决定顺序。

### TCC 来源

1. 在同一规则类型内按规则 `name` 做字符串排序，生成从 `0` 开始的序号。
2. 基础优先级为 `(序号 + 1) * 2`，因此基础规则使用偶数优先级。
3. 基础 ID 为优先级加 `5,000,000`。
4. 只对跨境出向类型 `cn_abroad.gw` 生成反向规则；反向 ID 增加 `100,000,000`，反向优先级为基础优先级加 `1`。

### NAC Security Center 来源

基础优先级按 `(prio + 1) * 10,000 + nac_rule_id * 2` 推导。`prio` 和动作通常由 `subclass` 决定：

| subclass | 动作 | 默认 prio | 其他行为 |
|---:|---|---:|---|
| `1`、`2`、`3` | 放行 | `1` | 分别表示默认、源、目的白名单 |
| `4`、`5`、`6` | 阻断 | `2` | 分别表示默认、源、目的黑名单，并默认开启记录；公网出向场景除外 |

跨境类型 `cn_abroad` 使用安全中心配置的原始优先级覆盖上述默认 `prio`。注意它与 TCC 反向规则判断使用的 `cn_abroad.gw` 是不同的类型标识。

安全中心规则除 `sg_out.gw` 外通常生成反向规则；反向 ID 增加 `100,000,000`，反向优先级为基础优先级加 `1`。同优先级时，ID 较小的规则优先。

### Yunque / MySQL 来源

Yunque 规则使用用户设置的优先级，不做来源级重算。只有 `reversed=true` 时生成反向规则；反向 ID 增加 `100,000,000`，反向优先级为原优先级加 `1`。

### Honeycomb 来源

Honeycomb 按添加顺序分配优先级，起点为 `10,000`。同优先级时 ID 较小的规则优先。Honeycomb 生命周期会为规则生成反向规则：管理面生成后交给 NSG 后端透传，反向 ID 增加 `100,000,000`，反向优先级为原优先级加 `1`。公网出向规则仍受“不生成反向规则”的全局例外约束。

## 已知限制

### NAC Security Center 的传输层协议可能在编译时丢失

安全中心来源即使配置了 `protocol`，NSG 后端的第一阶段解析也可能忽略该字段，导致数据面编译规则的 `L4_PROTO` 成为通配。看到编译前规则带 TCP、UDP 或 ICMP，而编译后规则显示传输层通配时，应将这个来源限制列为首要原因，不能断言两份规则完全一致。

核查时分别查询 normalize 结果与编译后结果，并明确指出差异发生在编译链路；不要由 CLI 擅自补回协议。

### NAC Security Center 的仅目的端口规则可能被丢弃

安全中心来源如果只配置 `DST_PORT`，而源、目的两侧都没有 IP、PSM 或域名，NSG 后端会在解析时将其判为非法并静默丢弃，即使端口本身有效。相同形态的 Yunque、TCC 或 Honeycomb 来源规则在当前实现中可能仍会下发。

这说明“`SRC_ID` 与 `DST_ID` 不能同时为通配”的规范在历史来源中执行不一致。诊断“控制面存在但数据面不存在”的端口规则时，必须同时检查来源与两侧身份字段；不能只检查端口，也不能把其他来源的成功下发推断为安全中心同样支持。
