# Create or update AGW BFFv2 routes

This reference covers related BFFv2 workflows:

1. update backend IDL first, then refresh existing BFFv2 type DSL
2. create a new BFFv2 route, optionally after the backend IDL update
3. batch create new BFFv2 routes across one or more thrift backend PSMs; batch creation is automatic and does not provide per-route IDL/DSL review

The main design goal is to keep users out of raw AGW config internals. Use render/DSL workspace/plan commands to produce reviewed config files, then submit config explicitly.

## Inputs to collect

- `site`: usually `cn`
- `psm` or `service_id`
- target env, for example `ppe_demo`
- route to copy, preferably existing `bff_key` or `path:method` for single-route workflows
- new route path and method, or a batch route map `{ thrift_backend_psm -> [method/path/rpc_method] }`
- backend API in protocol-aware form: `thrift:example.backend.service:GetItem` for single-route render workflows that need DSL review
- batch route spec in `<thrift-backend-psm>:<METHOD>:<PATH>:<RPC_METHOD>` form for multi-route automatic batch creation
- template name, usually from `agw bffv2 template get`
- whether backend IDL should be updated before creating the route
- whether to submit config only or also create a publish order

## Protocol values

| Protocol      | `svr_type` | Meaning                                   |
| ------------- | ---------: | ----------------------------------------- |
| `thrift`      |          0 | RPC service, Thrift protocol              |
| `http`        |          1 | HTTP service with IDL                     |
| `http-no-idl` |          2 | HTTP service without IDL                  |
| `tcc`         |          3 | TCC config                                |
| `rpc-http`    |          4 | Backend supports both RPC Thrift and HTTP |

## Description defaults

When the user does not provide a config or publish description, use a concise default and append `(via bytedcli agw)` so reviewers can see the config was generated by bytedcli.

Recommended defaults:

| Operation                      | Default description                                                      |
| ------------------------------ | ------------------------------------------------------------------------ |
| Backend IDL update config      | `update BFFv2 backend <backend-psm> IDL to <version> (via bytedcli agw)` |
| Multiple backend IDL updates   | `update BFFv2 backend IDLs (via bytedcli agw)`                           |
| New BFFv2 route config         | `add BFFv2 route <METHOD> <PATH> (via bytedcli agw)`                     |
| Publish order for route change | `publish BFFv2 route <METHOD> <PATH> (via bytedcli agw)`                 |

If the user gives a description, keep their wording but append ` (via bytedcli agw)` unless it is already present.

## Version model

Use explicit version names in notes and reports:

| Name                  | Meaning                                                  |
| --------------------- | -------------------------------------------------------- |
| `BASE_VERSION`        | target env current config before changes                 |
| `IDL_UPDATED_VERSION` | config version created after backend IDL update          |
| `FINAL_VERSION`       | config version created after adding/updating BFFv2 route |

Do not confuse a newly-created config version with the env current version. Always re-read env current config when the user says “当前泳道配置”.

## Output file defaults

Config plan files are user-reviewable artifacts, so keep them easy to find.

- If the user passes `--output-file`, use that path for the final config plan.
- For single-route `route create` that needs render and does not use `--auto-render`, default to an artifact workspace under `./<service_slug>/<method_path_slug>/`. The final reviewed plan is written to `snapshots/route-plan.<timestamp>.json` inside that artifact.
- For single-route `--auto-render` or `--bff-config-file`, keep the existing default `./agw-bffv2-route-plan-<service-id>-<base-version>-<timestamp>.json`.
- For `backend-idl update`, keep `./agw-bffv2-backend-idl-plan-<service-id>-<base-version>-<timestamp>.json`.
- For `batch-route create`, keep `./agw-bffv2-batch-route-plan-<service-id>-<base-version>-<timestamp>.json`; batch creation remains automatic and does not create per-route DSL workspaces.
- Do not default to `/tmp`; users need the path for `agw config create --body-file` and may want to review the file after an agent run.
- Do not use a fixed `new-config.json` default, because repeated attempts can overwrite each other.
- Always report the chosen `output_file` / artifact `route_plan` and the exact next `agw config create --body-file ...` command.

When the user explicitly says they do not need to review request IDL or DSL for a single route, use `route create --auto-render`. It should still write the final config plan file, but it should not create `http-input.thrift`, `render-dsl.json`, or a DSL workspace unless the user asks to save debug artifacts.

## Workflow A: update backend IDL only

Use this when the user only wants to update an existing BFFv2 backend IDL version and refresh existing BFFv2 type DSL.

```bash
# 1. Read env current config and record BASE_VERSION
bytedcli --site cn --json agw config get \
  --service-id 12345 \
  --env ppe_demo \
  --need-all-config

# 2. Generate updated config; this fetches BAM IDL, updates or appends
#    bff_v2_backends_config by protocol+PSM, calls batch_render_with_idl,
#    and writes a full config file. It does not submit.
bytedcli --site cn --json agw bffv2 backend-idl update \
  --service-id 12345 \
  --version <BASE_VERSION> \
  --backend-idl thrift:example.backend.service:1.0.21 \
  --backend-idl http:example.http.backend:2.0.3 \
  --description "update upstream idl" \
  --output-file updated-backend-config.json

# 3. Submit config. Do not pass --bff-backends-from-cfg-ver here,
#    because this config body intentionally carries the new bff_v2_backends_config.
bytedcli --site cn --json agw config create --body-file updated-backend-config.json --description "update upstream idl"
```

Record the returned version as `IDL_UPDATED_VERSION`.

Notes:

- `--backend-idl` is repeatable for multi-backend updates.
- If `protocol+PSM` already exists, the backend IDL config is updated.
- If `protocol+PSM` does not exist, a new backend config item is appended.
- If the target version is lower than the current configured version, the command blocks as a downgrade warning; pass `--allow-downgrade` only when the downgrade is intentional.

## Workflow B: update backend IDL, then create a new BFFv2 route

Use this when the new route must be rendered against the new backend IDL version.

### 1. Update backend IDL first

Run Workflow A and record `IDL_UPDATED_VERSION`.

### 2. Render the new route from `IDL_UPDATED_VERSION`

Do not render against `BASE_VERSION`; it may still contain the old backend IDL.

```bash
bytedcli --site cn --json agw bffv2 request-idl create \
  --service-id 12345 \
  --version <IDL_UPDATED_VERSION> \
  --template default \
  --backend-api thrift:example.backend.service:GetItem \
  --http-method GET \
  > render-idl-output.json
```

Extract `data.result.idl` into `http-input.thrift`, then render DSL. If `http-input.thrift` or any request IDL config changes, rerun `dsl create` with the latest file. The refresh updates `type_dsl` only; keep existing `handle_dsl` unchanged and do not reuse an older `type_dsl`.

```bash
bytedcli --site cn --json agw bffv2 dsl create \
  --service-id 12345 \
  --version <IDL_UPDATED_VERSION> \
  --template default \
  --backend-api thrift:example.backend.service:GetItem \
  --req-idl-file http-input.thrift \
  --purpose create \
  > render-dsl-output.json
```

Extract `data.result` into `render-dsl-config.json`.

### 3. Review DSL through workspace

```bash
bytedcli --site cn --json agw bffv2 dsl-workspace import \
  --bff-config-file render-dsl-config.json \
  --output-dir ./bffv2-dsl
```

Ask the user to review and edit only `HANDLE_DSL` sections in `*.dsl.ts`. Keep `TYPE_DSL` unchanged.

Pack after review:

```bash
bytedcli --site cn --json agw bffv2 dsl-workspace export \
  --workspace ./bffv2-dsl \
  --output-file reviewed-bff-config.json
```

### 4. Generate route plan from `IDL_UPDATED_VERSION`

```bash
bytedcli --site cn --json agw bffv2 route create \
  --service-id 12345 \
  --base-version <IDL_UPDATED_VERSION> \
  --path /demo/test2 \
  --method GET \
  --bff-config-file reviewed-bff-config.json \
  --output-file new-route-config.json \
  --copy-route-from <existing-bff-key> \
  --bff-backends-from-cfg-ver <IDL_UPDATED_VERSION>
```

Notes:

- `bff_key` is generated automatically and returned in JSON output.
- Omit `--frontend-idl-method-name` by default. Add it only when client IDL method names would conflict.
- It is okay to use `--bff-backends-from-cfg-ver <IDL_UPDATED_VERSION>` here because the route plan reuses the already-updated backend config.

### 5. Submit final config

```bash
bytedcli --site cn --json agw config create \
  --body-file new-route-config.json \
  --bff-backends-from-cfg-ver <IDL_UPDATED_VERSION>
```

Record the returned version as `FINAL_VERSION`.

### 6. Verify final version

```bash
bytedcli --site cn --json agw bffv2 route get --explain \
  --service-id 12345 \
  --version <FINAL_VERSION> \
  --bff-key <GENERATED_BFF_KEY>
```

Verify:

- route path/method
- generated `bff_key`
- `frontend_idl_method_name` is empty unless intentionally set
- backend protocol and `svr_type`
- backend PSM/method
- template and DSL mode

### 7. Publish if requested or authorized

PPE order:

```bash
bytedcli --site cn --json agw publish order create --target ppe \
  --service-id 12345 \
  --version <FINAL_VERSION> \
  --env ppe_demo \
  --description "add BFFv2 route /demo/test2"
```

Check status:

```bash
bytedcli --site cn --json agw publish order get --publish-id <publish-id>
```

For online, use `agw publish order create --target online`; do not use direct publish semantics for online.

## Workflow C: create a new BFFv2 route without backend IDL update

Use this when current `bff_v2_backends_config` already contains the desired backend IDL version.

### Option 1: review DSL before planning config

1. Resolve service and read env current config. Record `BASE_VERSION`.
2. Run single-route `route create` with `--template` and `--backend-api` but without `--auto-render`; this creates `<service_slug>/<method_path_slug>/dsl-workspace` for IDL/DSL review.
3. Edit `dsl-workspace/request.idl.thrift` or `HANDLE_DSL` sections as needed. If request IDL changes, rerun `agw bffv2 dsl create` from the artifact/workspace so only `TYPE_DSL` refreshes and `HANDLE_DSL` stays unchanged.
4. After review, run `agw bffv2 route create` from the artifact/workspace to pack DSL and write `snapshots/route-plan.<timestamp>.json`.
5. Submit with `agw config create --body-file <route-plan> --bff-backends-from-cfg-ver <BASE_VERSION>`.

### Option 2: skip request IDL/DSL review

Use this only when the user explicitly says they do not need to review generated request IDL or DSL. The command renders IDL/DSL in memory and writes only the final config plan file.

```bash
bytedcli --site cn --json agw bffv2 route create \
  --service-id 12345 \
  --base-version <BASE_VERSION> \
  --path /demo/test2 \
  --method GET \
  --auto-render \
  --template default \
  --backend-api thrift:example.backend.service:GetItem \
  --copy-route-from <existing-bff-key> \
  --bff-backends-from-cfg-ver <BASE_VERSION>
```

If `--output-file` is omitted, the default file path is `./agw-bffv2-route-plan-<service-id>-<base-version>-<timestamp>.json`.

## Workflow D: batch create BFFv2 routes

Use this only when the user wants to create multiple BFF2.0/BFFv2 routes, possibly across multiple thrift backend PSMs, with the same BFFv2 rule template. `batch-route create` currently supports thrift backends only; HTTP/TCC/RPC-HTTP backends are not supported by this flow yet. It is an automatic generation flow and does not provide per-route IDL/DSL review. For a single route, use `route create`; add `--auto-render` only when DSL review is not needed.

### 1. Collect inputs

Collect:

- `site`, usually `cn`
- `service_id`
- target env/current config version (`BASE_VERSION`)
- BFFv2 template name
- thrift route map: `{ thrift_backend_psm -> [method/path/rpc_method] }`
- optional target BFF group name for the new routes
- whether any backend PSM or RPC method needs a backend IDL update

Each `--route` value must include the thrift backend PSM:

```text
<thrift-backend-psm>:<METHOD>:<PATH>:<RPC_METHOD>
```

Example:

```bash
bytedcli --site cn --json agw bffv2 batch-route create \
  --service-id 12345 \
  --base-version <BASE_VERSION> \
  --template default \
  --route example.backend.service:GET:/batch/test1:GetItem \
  --route example.backend.service:GET:/batch/test2:GetMyPing \
  --route example.other.backend:POST:/batch/test3:CreateItem \
  --group demo-group \
  --create-group \
  --output-file batch-route-config.json
```

For larger batches, use `--routes-file` with this shape. `group_name` is optional; it overrides the global `--group` for that route.

```json
{
  "example.backend.service": [
    {
      "http_method": "GET",
      "path": "/batch/test1",
      "rpc_method": "GetItem",
      "group_name": "demo-group"
    },
    { "http_method": "GET", "path": "/batch/test2", "rpc_method": "GetMyPing" }
  ],
  "example.other.backend": [
    { "http_method": "POST", "path": "/batch/test3", "rpc_method": "CreateItem" }
  ]
}
```

### 2. Validate backend PSM and methods

`batch-route create` validates that every thrift backend PSM exists in the base config `bff_v2_backends_config` with `svr_type=0` and that every `rpc_method` exists in that thrift backend's current IDL methods.

If thrift thrift backend PSM or method is missing, `batch-route create` returns structured issues and a hint to update thrift backend IDL first.

### 3. If thrift backend PSM or method is missing, update backend IDL first

Do not direct-run batch creation against stale backend config. First generate and submit an intermediate backend-IDL config:

```bash
bytedcli --site cn --json agw bffv2 backend-idl update \
  --service-id 12345 \
  --version <BASE_VERSION> \
  --backend-idl thrift:example.backend.service:1.0.21 \
  --backend-idl thrift:example.other.backend:2.0.3 \
  --output-file updated-backend-config.json

bytedcli --site cn --json agw config create \
  --body-file updated-backend-config.json \
  --description "update BFFv2 backend IDL"
```

Record the returned version as `IDL_UPDATED_VERSION`. Batch creation must use this intermediate version, not the old `BASE_VERSION`.

### 4. Generate the batch route config plan

If backend IDL was updated, use `IDL_UPDATED_VERSION`; otherwise use `BASE_VERSION`.

```bash
bytedcli --site cn --json agw bffv2 batch-route create \
  --service-id 12345 \
  --base-version <IDL_UPDATED_VERSION> \
  --template default \
  --routes-file routes.json \
  --output-file batch-route-config.json
```

`batch-route create` only writes a local config plan. It does not create a config version or publish.

Do not add `--bff-backends-from-cfg-ver` to this command. The generated plan is based on a full `origin_config` and should include the required backend config.

### 5. Submit the final batch config

```bash
bytedcli --site cn --json agw config create \
  --body-file batch-route-config.json \
  --description "batch add BFFv2 routes"
```

Record the returned version as `FINAL_VERSION`.

### 6. Verify final routes

```bash
bytedcli --site cn --json agw bffv2 route list \
  --service-id 12345 \
  --version <FINAL_VERSION> \
  --group demo-group

bytedcli --site cn --json agw bffv2 route get --explain \
  --service-id 12345 \
  --version <FINAL_VERSION> \
  --path /batch/test1 \
  --method GET
```

Verify each route's path, method, backend PSM/RPC method, template, DSL mode, generated `bff_key`, and `group_name` when a group was requested.

### 7. Publish only when explicitly requested or authorized

If the user wants a publish order, use the existing publish order flow after `FINAL_VERSION` is created. For online, use `agw publish order create --target online`; do not use direct publish semantics.

## Common pitfalls

- Do not render a new route from `BASE_VERSION` after you have created `IDL_UPDATED_VERSION`; the new route would use stale backend types.
- Do not reuse old `type_dsl` after request or backend IDL config changes. Rerun `agw bffv2 dsl create` with the latest IDL before `dsl-workspace`, `dsl-workspace export`, or route plan creation; this refresh updates `type_dsl` only and should preserve existing `handle_dsl`.
- Do not run `batch-route create` when any backend PSM or RPC method is missing from the base config. First update backend IDL with `backend-idl update`, submit the intermediate config, then batch-create routes from `IDL_UPDATED_VERSION`.
- Do not use the old `BASE_VERSION` for batch route creation after backend IDL has been updated; use `IDL_UPDATED_VERSION`.
- Do not pass `--bff-backends-from-cfg-ver` when submitting the backend IDL update config itself.
- Do pass `--bff-backends-from-cfg-ver` when submitting a single route-only config that reuses an existing backend config version.
- Do not pass `--bff-backends-from-cfg-ver` to `batch-route create` or to the final `config create` for the batch plan.
- Every batch `--route` must include its thrift backend PSM. Do not assume all routes belong to the same backend.
- Do not hand-pick `bff_key`; let `route create` or `batch-route create` generate it.
- Do not set `--frontend-idl-method-name` unless client IDL generation would conflict.
